# To B 产品认知与设计原则（完整参考版）

本文是 `tob-product-principles.md`（精简触发核心，auto 加载）的**完整教学参考版**，`inclusion: manual`——只在显式 `#tob-product-principles-full` 调用时加载。精简核心给"核心判断 + 五条第一性认知 + 十一透镜速览 + 十二问自检"，够日常触发用；本文把每条透镜的检查问题、七步设计方法和理论来源全部展开，供需要深推时查阅。

结构分四层：**第一性认知**（§一）给底层框架，**判断透镜**（§二~§十二）给逐项检查，**设计方法**（§十三）给可执行步骤，**最小自检**（§十四）给动手前的收口。它是通用的 To B 判断透镜；落到具体项目时，产品事实与设计取舍以项目自己的产品/原则文档为准，本文只提供判断视角。

核心判断：**一个 To B 产品是否成立，不取决于功能是否可用，而取决于——某类组织在真实处境下，是否因它更低成本、更低风险或更高质量地取得了一个重要结果，且供应商能重复交付、长期维持。客户结果、组织采用、供应商经济性，漏掉任何一项，都可能做出「功能可用但产品不成立」的系统。**

## 一、五条第一性认知（底层框架）

先立框架，后面的判断透镜都是这五条的操作化。

1. **To B 产品服务的是组织结果。** 产品存在的理由，是让某类组织在特定处境下，以更低成本、更低风险或更高质量取得一个重要结果——不是交付功能。
2. **最小设计单元是「组织动作」，不是页面/按钮/接口。** 一个有意义的产品单元是一条完整链：触发情境 → 业务对象 → 当前状态 → 参与角色 → 判断依据 → 执行动作 → 结果 → 责任与证据。
3. **客户成功与供应商成功必须同时成立。** 只有客户成功而供应商持续亏损，退化成项目制服务；只有供应商标准化而客户拿不到结果，就是卖不出或留不住的产品。
4. **复杂度无法消失，只能被正确安置。** 好产品不假装复杂性不存在，而是决定它由谁承担、承担者是否看得见并处理得了。
5. **演进不是增加功能，而是提高稳定价值的覆盖范围。** 功能数量增加只说明系统变大，不证明产品变强。

## 二、先判断「客户要取得的组织结果」，再谈功能

企业购买的不是功能，而是一次有风险的组织改变。客户在某个具体处境下要取得「进展」，这个进展同时包含功能、社会关系和心理感受。所以需求不能只写成「输入 X，输出 Y」。客户要的结果分层，越往后越接近愿意付费或切换的理由：功能诉求 → 工作效率 → 业务结果 → 责任风险 → 组织能力。

检查：
- 谁在什么处境下发起？他要作出什么判断？
- 判断错了谁承担后果？
- 这个结果落在哪一层（功能/效率/业务结果/责任风险/组织能力）？是否足够重要到值得付费或切换？
- 产出如何进入后续动作，而不是停在「生成了一份东西」？

## 三、最小设计单元是「组织动作」，不是页面/按钮/接口

页面、按钮、接口或一次模型调用只是承载手段，不是完整产品单元。一个有意义的 To B 产品单元是一条完整的组织动作链：触发情境 → 业务对象 → 当前状态 → 参与角色 → 判断依据 → 执行动作 → 结果 → 责任与证据。定义只到「生成一份报告」还不够，要定义到「谁在什么情境下、对什么对象、依据什么、做出什么判断、交给谁、留下什么可复核的证据」。这条链足够完整，才能同时约束门面、状态、报告、证据和后端机制一起设计，而不是各做各的。

检查：
- 我在设计的是一条完整组织动作，还是一个孤立的页面/接口/字段？
- 触发情境、业务对象、当前状态、参与角色、判断依据、执行动作、结果、责任与证据——这八类缺了哪几类没说清？
- 产出之后接什么动作、由谁承接、留下什么证据可事后复核？
- 只有内核能力（如「能处理一个输入包」）不算一条组织动作；缺了情境、角色、判断和责任，就还没定义成产品单元。

## 四、To B 从来不是一个「用户」，先分清主体

至少存在：购买决策者、经济购买者、业务负责人、一线使用者、管理员与实施人员、技术与安全部门、管理层或审计方，以及供应商自身。每个主体的任务、痛点、收益不同。体验不等于界面体验，还包括采购者看到的价值、实施者的部署复杂度、管理员的掌控感、责任人需要的证据。

检查：
- 这个改动改善的是哪个主体的什么？
- 付费的人和使用的人是否同一个？他们各自的判断依据是什么？
- 是否只优化了一线操作界面，却没管采购、部署、掌控、举证？

## 五、真正的对手常是「现有应对方式」，不是竞品

客户没有你时会：继续人工、依赖资深人、用 Excel/脚本/内部页面、外包临时撑、忍受，或干脆什么都不做。「什么都不做」常常是真正要战胜的方案。

检查：
- 客户现在怎么扛？为什么一直没换？谁会反对改变？
- 切换成本有多少：数据迁移、系统集成、培训、权限审批、责任变化、对供应商的信任？
- 我们创造的改善是否大于「现有方案价值 + 切换成本」？

## 六、核心技术能力不等于完整产品

内核能跑，只证明有某种能力。客户能用的完整产品还包括入口、对象确认、状态与失败说明、结果阅读与证据下钻、导出、部署与环境适配、权限与数据访问说明、版本兼容范围、排障与支持。产品化的过程，是供应商逐步接过原来由客户和专家承担的拼装、解释、适配和成功责任。

检查：
- 客户是否还要自己找接口、拼事实、解释状态、组织报告？还在拼零件就还没产品化。
- 哪些是产品责任，哪些是明确的配套服务责任？
- 门面、状态、报告不是外围包装，它们承担「让客户真正获得能力」的责任。

## 七、价值在使用结果中兑现，不在签约或上线时

功能上线不等于价值成立；登录不等于采用；调用次数不等于业务效果；报告生成成功不等于帮客户完成了判断；续费也不能只靠商务关系。要沿链路验证：能力可运行 → 用户能完成任务 → 结果可用于决策 → 客户获得可观察改善 → 愿意持续使用和付费。

检查：
- 我现在是不是把「上线/登录/调用/生成成功」当成功了？那是代理指标，不是价值。
- 沿这条链，当前真正卡在哪一环？
- 我手上的证据在哪一级：访谈说过 < 愿意尝试 < 能完成并得到结果 < 愿持续付费？（分级详见 §十三·第 7 步）

## 八、客户成功与供应商成功必须同时成立（产品四类风险）

Marty Cagan 把产品风险分四类：**价值**（客户是否愿买、愿用）、**易用**（用户能否用起来）、**可行**（技术能否实现）、**商业可持续**（是否适合企业经营与合规约束）。To B 还要把这四类放进真实交付环境，客户侧与供应商侧同时体检：

- 客户侧：是否解决重要问题、是否容易采用、是否适配现有环境、是否可靠可解释、是否产生持续效果。
- 供应商侧：是否能重复销售、重复部署、控制现场差异、统一维护升级、保持合理交付成本与毛利。

只有客户成功而供应商持续亏损，退化成项目制服务；只有供应商标准化而客户拿不到结果，就是卖不出或留不住的产品。

检查：
- 这个改动/能力，客户侧和供应商侧的风险各是什么？哪一侧现在没答清？
- 四类风险里，当前最大的未验证风险是哪一类？是否该在投入建设前就先暴露它？
- 我是不是只顾了客户侧的价值，没算供应商侧的重复交付代价（或反过来）？

## 九、客户差异与供应商重复交付，是 To B 的核心矛盾

每家客户都有差异，但供应商不能为每家重做一套系统。真正的设计工作是识别：哪些是跨客户稳定的业务对象；哪些规则可参数化；哪些流程允许有限配置；哪些走扩展接口；哪些是现场实施；哪些只是单客户偶发要求；哪些差异会破坏产品主线、应明确拒绝。

检查：
- 这个差异是跨客户稳定对象，还是单客户偶发要求？
- 它该被参数化、配置、扩展接口、现场实施，还是拒绝？
- 配置化没有清晰的对象、约束、校验和版本管理时，只是把代码混乱换成配置混乱——复杂度没消失，只是转移给了配置模型、管理员和实施人员。

## 十、产品架构同时决定产品经济性

结构决定销售毛利、实施周期、客户满意度和能否规模化，不只是技术问题。

检查：
- 每多一种现场适配、多支持一个版本、多接受一个特例，谁维护？测试成本增加多少？后续升级是否仍可控？
- 数据模型、接口、配置、报告契约一旦发布，如何兼容历史数据和客户已有集成？
- 部署十个现场后，问题能集中修复，还是要逐场处理？

## 十一、复杂度无法消失，只能被正确安置

企业的组织、权限、规则、数据和例外本来就复杂。好产品不假装复杂性不存在，而是决定它由谁承担。

检查：
- 这次把复杂度放给了谁：产品内核、默认值、配置、接口、专业实施人员，还是客户？
- 承担者是否最合适、是否看得见它、能否处理它？
- 有没有把本该产品准确承载的复杂度，甩给了客户或一线使用者？

## 十二、按「长期存续对象」设计，不按可自由重写的新代码设计

产品一旦进生产，就形成历史数据、客户配置、外部接口、操作习惯、权限关系、业务责任、上下游依赖和已部署现场。演进对象 = 当前代码 + 已部署客户 + 历史数据 + 已公开契约 + 现场运行责任。这也是企业软件重构和升级远比新建功能难的原因。

检查：
- 这个改动是否破坏已部署客户、历史数据或已公开契约？迁移路径是什么？
- 演进是否扩大了「稳定价值的覆盖范围」（支持新处境、减少客户困难、把现场特例提炼成产品能力、降低单客户边际交付成本），还是只增加了功能数量？
- 已有客户能否安全升级？

## 十三、设计方法：从现场到证据的七步

把上面的认知和透镜收敛成七个连续判断，按顺序走，每步先产出可被确认的东西，再进入下一步：

1. **先还原现场。** 记录真实事件、角色、对象、信息缺口、协作摩擦和失败后果；先不整理模块，更不急着生成需求清单。产物是一段能被现场人员确认的事务描述。
2. **找到客户要取得的关键结果。** 区分功能诉求 / 工作效率 / 业务结果 / 责任风险 / 组织能力；越接近愿付费的结果，产品定义越稳定。
3. **识别真实替代方案和切换阻力。** 客户现在怎么处理、为何一直没换、谁会反对；改善必须 > 现有方案价值 + 切换成本（数据迁移、集成、培训、权限审批、责任变化、对供应商的信任）。
4. **定义最小产品承诺。** 明确帮谁、在什么条件下、完成什么结果，以及明确不承诺什么。远期愿景不能污染当前交付边界。
5. **补齐完整产品（走一遍采用链）。** 发现 → 理解价值 → 申请/部署 → 配置接入 → 发起使用 → 了解状态 → 读取结果 → 核验证据 → 采取行动 → 保存/分享 → 获得支持；凡是必须发生、但客户无法自行完成的环节，都是产品责任或明确的配套服务责任。
6. **沿稳定对象与变化边界设计结构。** 先识别长期稳定对象（如核心业务对象、证据、判断、建议、运行实例、报告），再判断不同现场的变化发生在哪；抽象（Provider / Adapter / 领域包等）服务真实变化边界，不因技术整洁而提前建设。
7. **用证据推动演进（四级证据，逐级更强）。** ①客户确实存在这个问题 → ②愿意尝试这种解决方式 → ③能完成任务并获得结果 → ④愿持续使用、采购、续费或扩大使用。访谈只证明客户说过什么；真实使用、处置结果、续费和扩展才是更强证据。

## 十四、产品判断前的最小自检

涉及 To B 产品需求、能力取舍、范围或路线判断时，先回答；答不清就不要先扩范围或先建设施：

1. 哪类组织、在什么处境、要取得什么结果？结果落在功能/效率/业务结果/责任风险/组织能力哪一层？
2. 我设计的是一条完整组织动作（情境/对象/状态/角色/判断依据/动作/结果/责任与证据齐全），还是一个孤立页面或接口？
3. 哪些主体参与，谁付费，谁使用，谁承担失败后果？
4. 客户现在怎么应对，切换成本是什么？改善是否大于「现有方案价值 + 切换成本」？
5. 这件事必须软件承载吗，还是规则、配置、服务或「什么都不做」就够？
6. 完整产品还缺哪一环（采用链哪一步客户过不去）？
7. 客户侧和供应商侧是否都成立？四类风险（价值/易用/可行/商业可持续）里最大的未验证风险是哪一类？
8. 这是跨客户稳定对象，还是单客户特例？该参数化、配置、扩展、现场实施，还是拒绝？
9. 它的经济性代价是什么（维护、版本、现场、兼容历史数据与已公开契约）？
10. 复杂度被放到了谁身上？承担者看得见、处理得了吗？
11. 用什么证据算它成立（不是访谈说过，而是能完成、有改善、愿付费）？现在在四级证据的哪一级？
12. 本次明确不做什么？

## 十五、与其它原则的分工

- 通用 To B 判断透镜：精简核心 `tob-product-principles.md`（auto）+ 本完整参考版（manual）。
- 具体项目的产品事实、设计取舍与阶段范围：**项目自己的产品/原则/阶段文档**（阶段范围以其为唯一权威）。
- 问题前提红队：`question-clarification`；代码与系统设计：`software-design-principles`。

出现张力时，本文只提供判断角度，让位于更具体、更贴近当前项目的产品/阶段权威。
