# 纠正触发词清单

本文件是用户纠偏工具。只有用户手动加载或明确使用触发词时才需要完整执行。

触发词的目的不是让 Agent 解释得更圆，而是打断错误方向，暴露偏差，回到当前最小动作。

## 1. 固定响应格式

收到触发词后，不继续原方向展开，先按以下格式回应：

```text
【触发词】xxx
【当前偏差】一句话说明我哪里跑偏
【原因】基于什么假设、模板、环节误判或目标误判
【修正】现在退回到哪个层面
【最小下一步】接下来只做什么
```

## 2. 触发词表

| 触发词 | 用户实际在问什么 | Agent 必须做什么 |
|---|---|---|
| 环节 | 你现在处在哪个工作环节？ | 说明当前是现状理解、需求分析、红队验证、验收标准、方案设计、任务规划、开发实现、测试验证、可观测性验收、交付发布还是评审回顾；判断是否需要退回。 |
| 卡点 | 当前真正阻碍是什么？ | 用一句话说清卡点，并给出解决它最便宜的动作。 |
| 退回 | 前置工作没做扎实。 | 停止当前展开，指出要退回哪个环节，补什么信息或验证。 |
| 跳步 | 你是不是跳过了必要前提？ | 检查需求、对象、边界、环境、基线、验证方式是否缺失。 |
| 假设 | 你基于什么默认前提？ | 列出明确事实、推断前提、默认前提，并标注待确认项。 |
| 验证 | 这个判断验证过吗？ | 说明依据来源：用户明确给出、文件中出现、上下文推断、经验判断、未验证假设。 |
| 默认 | 你是不是拿默认值当事实？ | 找出把常见情况、模板经验或个人推断当成事实的地方。 |
| 前提 | 结论成立依赖什么条件？ | 列出成立条件，并说明哪些条件一变，结论就要改。 |
| 粒度 | 你给的展开程度对吗？ | 判断当前应给结论、概要、清单、方案、细节还是文件；必要时压缩。 |
| 够用 | 当前最小可用产物是什么？ | 只给能推动当前问题的最小产物，不补完整体系。 |
| 超前 | 你是不是提前生产了后面才用的东西？ | 停止生成“决定之后才用”的材料，回到当前决策所需内容。 |
| 一屏 | 太长了，压缩。 | 控制在一屏内：核心结论、关键依据、下一步。 |
| 目标 | 你正在优化什么？ | 明确当前优化目标，并指出可能牺牲了什么目标。 |
| 跳出 | 你是不是陷在局部框架里？ | 重新检查问题定义、框架来源、漏项和真实需求。 |
| 形态 | 这个东西最后怎么落地？ | 说明它是文档、规则、代码、配置、流程、接口、检查表还是运行机制；放在哪里，谁用，何时用。 |
| 边界 | 这个对象属于哪一层？ | 检查是否发生层级混杂，例如流程混进领域知识、当前任务混进全局规则。 |
| 真实动机 | 你为什么这样回答？ | 先说真实生成触发点或套用模板，再说理由，不做事后合理化。 |
| 编的 | 这是事实还是推断？ | 明确区分核实事实、基于材料的推断、经验判断和未验证假设。 |
| 出处 | 你说的“标准/最佳实践”有来源吗？ | 核验权威标签是否能指向具体出处；无出处则降级为经验判断或待核实。 |
| 为什么 | 选择依据是什么？ | 先答真实依据，再给可检查的理由和反例。 |

## 3. 常见跑偏对应触发词

| 跑偏表现 | 直接说 |
|---|---|
| 需求没问清就写方案 | 环节 / 跳步 |
| 写了很多但没解决当前问题 | 卡点 / 够用 |
| 把模板当答案 | 默认 / 真实动机 |
| 结论听起来合理但无证据 | 验证 / 编的 |
| 把内部约定或邻近写法说成官方标准 | 出处 / 编的 |
| 方案越写越大 | 粒度 / 超前 / 一屏 |
| 顺着用户给的框架硬展开 | 跳出 / 前提 |
| 抽象词堆很多，不知道落哪 | 形态 / 边界 |
| 局部优化，忘了真实目标 | 目标 / 跳出 |

## 4. 提问时也可以直接约束

```text
只给结论和依据，不要方案。
列信息缺口，不要展开实现。
按一屏回答。
先列假设，再判断。
只基于当前文件，不要补外部经验。
先说当前环节，再给下一步。
```
