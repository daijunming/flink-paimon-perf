# 项目代码审查手册

本手册规定“如何审”，不定义“系统事实是什么”。项目定位、阶段边界、模块职责、技术合同和语言细则分别以项目自己的产品/结构/技术文档为准。

核心规则：**合规轴全绿不等于设计轴健康。** lint、命名、测试、文件位置和注释是有用证据，但不能单独证明职责内聚、逻辑放置、行为正确、合同安全或系统可维护。

## 1. 审查启动：先钉住对象和范围

开始前必须写清：

- 审查对象、调用场景、当前工作环节、目标使用者与失败后果；
- 审查文件集、直接调用方/消费方、相关测试、运行入口与不审范围；
- 哪些是已查代码或运行事实，哪些是推断，哪些尚未验证；
- 本次目标是发现问题、验证某项属性，还是为重构建立证据。不要把“谨慎不立即改”写成“没有问题”。

先读取 `working-agreement.md`、`work-deviation-triggers.md` 与项目的产品/结构/技术事实文档；再按第 6 节加载对象对应的详细规则。

### 协调、并行与机械基线

默认由一个协调者保留问题定义、编排核心文件的深审、跨层综合和最终结论。只有证据互不依赖时才并行分派，例如各分析器、适配器、API 或前端的独立取证；不得把共享状态机、合同、编排主链路或跨层结论切碎交接。

在理解范围、合同和风险后，可运行可用的 lint、类型、复杂度、语句数、分支数、参数数或返回数检查作为**机械基线**。报告工具、配置、关键结果和未运行原因；阈值只提示“优先读哪里”，不自动等于违规或严重度。子任务负责工具无法可靠判断的关系、行为、消费方和设计问题，不重复把工具输出改写成结论。

## 2. 三轴审查矩阵

逐轴声明覆盖；某格不审时写“未审及原因”，不能静默省略。

### 层级：低层绿不覆盖高层

| 层级 | 必问问题 |
| --- | --- |
| 行 | 值、条件、异常、日志、资源与边界值是否表达真实语义？ |
| 函数 | 它只承担一个稳定职责吗？输入、输出、副作用、失败与测试边界清楚吗？ |
| 类/模块 | 单元是否因同一类变化而变化？领域逻辑、编排、I/O、展示是否糅杂？ |
| 包/依赖 | 依赖方向、物理放置、公共入口与测试边界是否符合项目结构？ |
| 系统/契约 | 路由、字段、状态组合、降级、兼容、权限与可观测性是否对消费方成立？ |
| 需求 | 当前实现是否仍服务真实对象、阶段范围、用户判断和验收标准？ |

### 维度：逐维过，不用一项代替另一项

默认检查：正确性、契约兼容、安全、可靠失效、性能资源、可观测、可测、可维护、数据语义。

每一维必须写“已查 / 未审 / 不适用”及理由。测试通过只能支撑被测试到的行为；不能自动支撑未覆盖的契约、并发、资源、降级、结构或需求结论。

### 视角：为属性选择配得上的证据

| 要判断的属性 | 最低可接受证据 |
| --- | --- |
| 命名、格式、显式目录规则 | 静态读、搜索、自动检查 |
| 职责内聚、逻辑放置、依赖方向 | 函数职责清单、引用图、类型/状态定义位置、目标目录同类邻居 |
| 关键行为、失败与状态转换 | 追调用链、相关测试、实际运行或最窄可复现路径 |
| 外部契约、兼容与爆炸半径 | 请求/响应定义、所有消费方、历史数据/兼容测试、运行入口 |
| 操作者可诊断、降级是否响亮 | 阶段日志/trace、失败样本、响应细粒度缺失与粗粒度成功的对照 |

**未查过的昂贵属性不得写“符合”“没有问题”或“边界清楚”。** 最多写“本次未验证”。被审文件的注释、docstring、命名和自述不能作为它自身边界正确的独立证据。

高影响发现必须由协调者复核原始代码、触发条件、直接消费方和反证路径后才可定性。高影响包括凭据/认证、稳定合同、全局失败、终态与降级语义、数据泄露和可能误导使用者的结论。记录“初始假设 → 复核证据 → 最终定性”；无法完成复核时降为观察项，不写成已发生事实。

## 3. 必做的独立取证动作

对每个重要函数、类或模块，至少完成与风险相称的以下动作：

1. 列出它实际做什么，而非只复述名称或注释；逐项问“它该住在这里吗”。
2. 搜索引用面和测试直接导入面；私有函数被独立消费通常是可拆分或错放信号。
3. 查它操作的类型、状态、合同或领域对象定义在哪里；装配 A 类型却远离 A 及其同类逻辑是错放信号。
4. 列出目标目录已有同类文件与职责；不看邻居，不能判断该搬到哪或是否已有 owner。
5. 对关键链路追到消费方和操作者：输入从哪来、状态如何终止、失败如何显现、谁据此行动。

这些动作是关系图视角的一部分，不替代运行验证或契约验证。

## 4. 本项目优先风险（按项目填）

按当前项目的爆炸半径排优先级——不同项目具体项不同，动手前把下列通用类别落成本项目的具体清单：

1. **正确性与数据语义**：是否把缺失、不可达、部分结果或范围外误说成结论；是否把未知补成 0、成功或健康；主键、时间语义、状态模型是否被悄悄改写。
2. **稳定对外合同**：版本字段、状态码/枚举、响应字段、白名单、对外摘要格式、配置键、降级语义是否被静默改变。把本项目的具体合同字段列在此处。
3. **降级与可观测**：不同的失败语义不得互相混同；粗粒度成功不得掩盖细粒度缺口；任何已采集来源的失败不得静默消失；是否允许继续并返回部分成功，必须服从范围、终态和证据合同。
4. **放置与上帝流程**：适配/协议层不写业务规则；编排层不吞领域解释；外部适配层不输出业务结论；不可由易变层决定最终稳定状态。数百行流程、独立可导入的私有逻辑、跨层装配都是优先信号。
5. **边界特定风险**：认证/权限、外部写操作、数据落盘、脱敏、前端只显示后端事实——按项目实际边界补。

## 5. 输出：发现、范围和结论

每条发现按以下格式输出，按影响和证据强度排序：

```text
[影响] 标题
位置：文件:符号或行
事实：已直接确认的代码、合同、运行或测试事实
问题：为何在本层级/维度成立，不能只说“违反原则”
后果：谁会看到什么错误、兼容风险或维护成本
证据：使用的视角与命令/调用链/消费方
最小修正：保持合同和现有 owner 的最小路径
验证：能证伪该问题的最窄检查
```

严重度由触发条件、受影响消费方、爆炸半径、可复现性和合同/安全后果决定，不由“函数很长”“有重复”或“看起来不优雅”直接决定。上帝方法、双梯子重复、位置敏感遮蔽、职责混合和散弹式修改点是结构信号；若尚未证明后果，写为结构脆弱性或观察项。

修复建议按决策归属分流，禁止混装：

- **编码阶段可收口**：已确认的异常隔离、日志补全、遮蔽 bug、过期注释；给出最小修改点和验证。
- **需设计评审**：脱敏策略、扩展轴、状态/严重度梯子、跨模块 owner 调整；说明问题、稳定边界和备选方案，不擅自实施。
- **需产品范围决策**：预留脚手架、能力去留、阶段边界；列出事实、成本和消费影响，不把个人偏好写成结论。

结论必须分四类：**事实**（已被代码/测试/配置/日志/运行直接证实）、**推断**（由证据推导但未直接验证）、**未验证项**（本次未覆盖的层级/维度/视角及原因）、**建议**（下一步最小行动，不伪装成当前事实）。

跨层审查收尾时回答：复杂度是否集中在编排主链路、应用工厂、状态判定或其它汇聚点？若是，指出哪些所有权决策被从设计阶段推迟到编码阶段；这是一条架构结论，不自动等于立即重构指令。

项目审计、跨模块评审或高影响发现应落盘到项目的审查/过程记录目录（独立审查文档）；局部审查也必须至少在报告中保留范围、方法、机械基线、发现、分流建议与明确不做事项。高影响发现保留初始定性和复核后定性。

没有发现时，也必须列审查范围、已跑证据和未覆盖项；不得把“没有报告 finding”写成“项目健康”。

## 7. 结论门禁

提交审查报告前逐项确认：

- 是否把合规轴与设计轴分开报告？
- 是否真的追过每个重要单元做什么、与谁共同变化、该住哪、谁依赖它？
- 是否把文件自述当成独立证据？
- 是否把测试绿、lint 绿或命名齐整越级推广为模块、契约或需求健康？
- 是否明确了没有审到的维度和原因？
- 是否把“暂不重构”的行动克制与“没有设计问题”的判断分开？

任一项为否时，收窄结论、补证据或明确标注未验证；不要盖“符合”章。

## 非目标

本手册不要求每次审查扫描全仓库，也不要求低风险局部修改走完整矩阵。审查深度随属性成本和爆炸半径调整；范围外项必须显式说明，而非默认通过。
