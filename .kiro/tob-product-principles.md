# To B 产品认知与设计原则（精简核心）

本文是做 To B/企业级产品判断时的**精简触发核心**：核心判断 + 五条第一性认知 + 十一透镜速览 + 十二问自检，够日常判断用。每条透镜的**检查问题、七步设计方法、理论来源**在完整参考版 `#tob-product-principles-full`（manual，按需 `#` 调用）。它是通用 To B 判断透镜；具体项目的产品事实、阶段范围与设计取舍以**项目自己的产品/阶段文档**为准，本文不重复。

核心判断：**一个 To B 产品是否成立，不取决于功能是否可用，而取决于——某类组织在真实处境下，是否因它更低成本、更低风险或更高质量地取得了一个重要结果，且供应商能重复交付、长期维持。客户结果、组织采用、供应商经济性，漏掉任何一项，都可能做出「功能可用但产品不成立」的系统。**

## 一、五条第一性认知（底层框架）

1. **服务的是组织结果**，不是交付功能——让某类组织在特定处境下更低成本/风险、更高质量取得一个重要结果。
2. **最小设计单元是「组织动作」**，不是页面/按钮/接口——一条完整链：触发情境 → 业务对象 → 当前状态 → 参与角色 → 判断依据 → 执行动作 → 结果 → 责任与证据。
3. **客户成功与供应商成功必须同时成立**——只客户赢供应商亏 = 退化成项目制；只供应商标准化客户拿不到结果 = 卖不出/留不住。
4. **复杂度无法消失，只能被正确安置**——决定它由谁承担、承担者是否看得见并处理得了。
5. **演进 = 提高稳定价值的覆盖范围**，不是增加功能——功能变多只说明系统变大，不证明产品变强。

## 二、判断透镜速览（逐条检查见完整版）

1. 先判断客户要取的**组织结果**（分层：功能→效率→业务结果→责任风险→组织能力），再谈功能。
2. 设计的是**完整组织动作链**，还是孤立页面/接口/字段？八要素缺哪几类没说清？
3. To B 不是一个「用户」，先**分清主体**（购买/经济购买/业务负责/一线/管理员实施/技术安全/审计/供应商）——体验 ≠ 界面体验。
4. 真正的对手常是**现有应对方式**（含「什么都不做」）——改善须 > 现有方案价值 + 切换成本。
5. **核心技术能力 ≠ 完整产品**——入口/状态/失败说明/证据下钻/部署适配/权限/兼容/排障都是产品责任；还在拼零件就没产品化。
6. **价值在使用结果中兑现**——上线/登录/调用/生成成功都是代理指标；沿「能跑→能完成任务→可决策→可观察改善→愿付费」看卡在哪。
7. **客户侧与供应商侧同时体检**（Cagan 四类风险：价值/易用/可行/商业可持续）——最大未验证风险是哪一类？
8. **客户差异 vs 供应商重复交付**是核心矛盾——这个差异该参数化/配置/扩展接口/现场实施，还是拒绝？（配置化不消灭复杂度，只转移）
9. **架构同时决定经济性**——每多一种现场适配/版本/特例谁维护？契约发布后如何兼容历史与已有集成？
10. **复杂度只能安置**——这次放给了谁（内核/默认值/配置/接口/实施人员/客户）？承担者看得见、处理得了吗？
11. 按**长期存续对象**设计（当前代码 + 已部署客户 + 历史数据 + 已公开契约 + 现场责任）——改动是否破坏已部署客户/历史数据/已公开契约？

## 三、产品判断前的最小自检

涉及 To B 产品需求、能力取舍、范围或路线判断时，先回答；答不清就不要先扩范围或先建设施：

1. 哪类组织、在什么处境、要取得什么结果？结果落在功能/效率/业务结果/责任风险/组织能力哪一层？
2. 我设计的是一条完整组织动作（情境/对象/状态/角色/判断依据/动作/结果/责任与证据齐全），还是一个孤立页面或接口？
3. 哪些主体参与，谁付费，谁使用，谁承担失败后果？
4. 客户现在怎么应对，切换成本是什么？改善是否大于「现有方案价值 + 切换成本」？
5. 这件事必须软件承载吗，还是规则、配置、服务或「什么都不做」就够？
6. 完整产品还缺哪一环（采用链哪一步客户过不去）？
7. 客户侧和供应商侧是否都成立？四类风险（价值/易用/可行/商业可持续）里最大的未验证风险是哪一类？
8. 这是跨客户稳定对象，还是单客户特例？该参数化、配置、扩展、现场实施，还是拒绝？
9. 它的经济性代价是什么（维护、版本、现场、兼容历史数据与已公开契约）？
10. 复杂度被放到了谁身上？承担者看得见、处理得了吗？
11. 用什么证据算它成立（不是访谈说过，而是能完成、有改善、愿付费）？现在在四级证据（存在问题 < 愿尝试 < 能完成得结果 < 愿持续付费）的哪一级？
12. 本次明确不做什么？

## 四、与其它原则的分工

- 通用 To B 判断透镜：本文（精简核心）+ `#tob-product-principles-full`（完整参考，manual）。
- 具体项目的产品事实（做什么、不做什么、稳定契约）与阶段范围：**项目自己的产品/阶段文档**（阶段范围以其为唯一权威，本文不反向扩大）。
- 问题前提红队：`question-clarification`；代码与系统设计：`software-design-principles`。

本文只提供判断角度，出现张力时让位于更具体、更贴近当前项目的产品/阶段权威。
