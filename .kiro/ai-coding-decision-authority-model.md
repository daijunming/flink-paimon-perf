# AI 编程决策权泄漏与恢复模型（通用 · 可移植）

本文是**通用**模型：在 AI 编程协作中，人的决策主导权会从哪里泄漏、要保护什么、失控后如何恢复。它**可移植**——把它复制进项目的 `.kiro/steering/` 并按需选择 inclusion（默认 `manual`，或只把 §0 速用 + 硬规则设为常驻）；不要整份设 always，避免它自己变成"规则压力集中"。

它是**风险与控制模型**，不是研发流程模型；与项目已有的"工作环节 / 流程"类指导**配合**使用（见 §7），不替代。

核心判断：**AI 生成的代码能跑 ≠ 人还掌控着这个项目。** 要掌控的是"人的知情决策主导权"；它会沿五条通道逐步泄漏进 AI 的输出节奏。本模型用于**定位在哪设控制点**，不用于给失控打分。

## 0. 一屏速用

**圆心（要保护的）**：人的**知情**决策主导权——在理解了对象、目标、方案、状态、证据之后，仍握有目标权、解释权、取舍权、放行权、撤销权。名义上点"确认"不算。

**一个元控制**：**显式决策交还**——到下列触发时点，AI 必须停下，把决策摆成"选项 + 各自代价 + 建议"交人定，**不把决策吸进自己的输出节奏**。

**六个触发时点 → 六条硬规则**（到了就交还）：

| 触发时点 | 硬规则 |
|---|---|
| 动语义承重件（模型 / 契约 / 状态机 / 主键 / schema） | 没有"改了哪些对象·关系·语义·受影响契约"的差异说明，不接受边界变化 |
| 引入新术语 / 框架 / 模式 / 抽象 / 依赖 | 没建立与当前问题的必要关系、没说清代价与更简替代，不引入 |
| 单轮输出将超过人的审查带宽 | 拆分输出：事实 / 方案 / 风险 / 代码 / 验证分开，一次只要人做一个主决定 |
| 目标或 Non-goals 变化 | 停下重新确认，不在多轮里悄悄扩范围 |
| 宣称"完成 / 通过" | 没有对**真实目标**的完成证据（非测试绿等代理），不允许转"完成" |
| 高影响 / 不可逆 / 大爆炸半径操作前 | 没有可信回退路径（基线 + 撤销 + 清理），不执行 |

**一条恢复轴（正交兜底）**：高影响变更前**先**备好可信基线、影响隔离、变更追踪、撤销 / 恢复 / 清理 / 重放路径——恢复能力必须前置，出事后不会自动拥有。

以下是这套操作核心背后的完整模型与理由。

## 1. 模型总览

```text
对象认知通道（系统是什么、要变成什么）
    通道1 系统语义与概念模型漂移
    通道2 术语与抽象劫持
                                    ├──►  ◎ 圆心：人的知情决策主导权
协作过程通道（目标怎么保持、信息怎么审、任务怎么推进和证明）
    通道3 信息载荷过载
    通道4 目标与任务主旨漂移
    通道5 任务状态与完成证据失真

可回退性与恢复韧性   ⊥ 横贯所有通道（失控后限制爆炸半径、恢复到最近可信状态）
```

五条通道解释决策权**怎样逐步泄漏**；圆心是**共同保护的目标**；恢复轴控制**失控后的损失**。这是一张控制拓扑图，不是并列分类表。

## 2. 圆心：人的知情决策主导权

一个人最后点"确认"，若他看不懂系统模型、不理解新术语、没审完信息、不知目标已变、信了错误的完成信号——这只是**名义确认**。真正的圆心是**知情**决策主导权，至少含五项：

- **目标权**：决定做什么、为什么、哪些不做（Non-goals）。
- **解释权**：决定系统对象与术语在本项目中的真实含义。
- **取舍权**：决定接受哪个方案、承担什么代价。
- **放行权**：决定是否进入实现、验收、发布。
- **撤销权**：发现错误时能停止、回退、恢复。

五条通道每失守一条，就削弱其中某项权利。

## 3. 五条泄漏通道

| 通道 | 失控形式 | 如何把决策权泄漏给 AI | 控制点：交还前必须交付 |
|---|---|---|---|
| 1 系统语义与概念模型漂移 | AI 重写了系统对象 / 关系 / 职责 / 运行语义，人不知情 | 人以为只在改实现，系统"概念账本"已被改写 | 当前模型、拟变更对象、语义差异、受影响契约 |
| 2 术语与抽象劫持 | 被不必要的新词 / 框架 / 抽象带走 | 人被迫在没理解的词汇上决策 | 术语定义、解决什么问题、必要性、代价、更简替代 |
| 3 信息载荷过载 | 单轮输出超过人能完整审查的量 | 人来不及审，"看着对就继续" | 事实 / 方案 / 风险 / 代码 / 验证分开；一次一个主决定 |
| 4 目标与任务主旨漂移 | 原始任务被多轮稀释 / 偏移 / 扩大 | 人还以为在做原任务，目标已被改写 | 原始目的、当前任务、范围变化、是否触碰 Non-goals |
| 5 任务状态与完成证据失真 | 分不清事实 / 推断 / 已实现 / 已验证 / 已验收；用代理信号冒充真实目标达成 | 人基于错误进度信号决策，或接受"假完成" | 已完成项、未验证项、真实证据、代理证据、进入下一状态的理由 |

**通道 5 是最后一道门**：前面模型 / 术语 / 目标即使已偏，只要这里验收仍可靠，问题还能拦；这里一失守，人就接受"假完成"。典型代理信号（都要识破）：写完代码 ≠ 完成 · 测试绿 ≠ 目标达成 · 命令返回 0 ≠ 数据正确 · 生成了报告 ≠ 完成了分析 · 有指标 ≠ 可观测 · 局部测试过 ≠ 全链路可靠 · 推断 ≠ 事实。

**通道各自作用不同、且相互放大，不是等权线性相加**：通道 1/2 决定人是否理解"在改什么"；通道 3 决定人是否有能力审查；通道 4 决定方向是否还对；通道 5 决定错误结果是否被当成完成。单条失守即可致严重后果（如主键 / 时间语义被改、目标被替换、测试绿冒充数据正确）；多条同失时风险放大。**用它定位控制位置，不用于机械打分。**

## 4. 恢复韧性轴（正交）

五条通道压低**失控发生概率**（防泄漏）；恢复轴压低**失控后的损失**（恢复）：

```text
风险损失 ≈ 失控概率 × 爆炸半径 × 恢复成本
```

回退 ≠ `git revert`：代码回退不等于系统恢复。完整恢复能力含：

- **可信基线**：知道回到哪个状态才算可信。
- **变更隔离**：一次变更只影响有限对象。
- **可定位**：知道 AI 改过什么、产出了什么。
- **可撤销**：代码 / 配置 / 文档能回退。
- **可恢复**：数据 / 状态 / 作业 / 环境能恢复。
- **可清理**：能清除错误生成的临时文件 / 表 / Topic / 快照 / 副作用。
- **可重放**：能从可信输入重跑并恢复结果。

数据平台（如流处理引擎 / 数据湖 / 表格式存储 / 消息队列等）尤其要提前想清：代码回退后已写入的数据、schema / 主键变更、已生成的快照 / 元数据、检查点 / 保存点、测试 topic 与临时路径、下游是否已消费错误结果。

**恢复能力必须前置**：没提前准备分支 / 检查点 / 备份 / 幂等脚本 / 清理路径，出事后不会凭空拥有恢复能力。

**按阶段裁剪**：只读 / 无副作用的项目，当前恢复轴很窄（git 回退 + 清理生成产物即可）；一旦项目开始写数据 / 改状态，才逐步补齐上面各项。不要为尚不存在的副作用提前建完整恢复机制（那本身就是通道 2 式的过度抽象）。

## 5. 显式交还协议

触发时点（§0）到达时，AI 执行：

1. **停** —— 不继续推进、不顺势扩大。
2. **命名** —— 明确"这是一个该你定的决策点"，属于哪条通道。
3. **摆选项** —— 给出可选路径 + 各自代价 / 风险，区分事实与推断。
4. **给建议但不代决** —— 可给推荐，但不自行进入下一步。
5. **等放行** —— 人做出选择后再继续。

这条协议是把圆心从口号变成行为的唯一操作内核。**新项目落地时**：通道 3/4/5 与恢复轴的部分触发可机械化（hook：按路径 / 工具名，在写语义承重件、宣称完成、执行破坏性操作时提醒并要求交还；注意 hook 按工具名 / 路径触发、不能按内容判语义，精确判断仍在 agent）；其余靠此协议作为常驻纪律。不要为全部通道都造机械——先上"完成门"和"危险操作确认"这两个收益最高的。

## 6. 横切机制（不是通道）

- **红队质询**：横向侦测，可攻击每条通道（概念是否被改写、术语是否必要、输出是否用过载掩盖问题、目标是否漂移、完成证据是否只是代理、回退是否真可用）。不是第六通道。
- **可观测性**：服务通道 5（状态 / 证据真实性）与恢复轴（是否达到回退条件、回退后是否真恢复）。是控制能力，不是失控通道。
- **评审 / 人工确认**：是"显式交还"的实现形式，按控制点分（概念契约评审、目标 Non-goals 评审、方案边界评审、验证证据评审、发布回退评审）。不是失控通道。

## 7. 与研发工作模式配合

本模型是风险模型（防什么、保护什么、如何恢复）；项目的**工作环节 / 模式**（现状理解 / 需求分析 / 验收标准 / 方案设计 / 建模 / 规划 / 实现 / 测试验收 / 可观测验收 / 交付 / 复盘）是流程模型（何时设控制点）。二者配合、不替代。参照映射（**是参照，不是每任务强制跑的矩阵**）：

| 工作模式 | 重点保护的通道 |
|---|---|
| 现状理解 | 通道 1、2 |
| 需求分析 / 验收标准 | 通道 4、5 |
| 方案设计 | 通道 2、1、4 |
| 工程对象建模 | 通道 1、3 |
| 任务规划 | 通道 3、5 |
| 开发实现 | 通道 4、1、恢复轴 |
| 测试与结果验收 | 通道 5 |
| 可观测性验收 | 通道 5、恢复轴 |
| 交付发布 | 放行权、恢复轴 |
| 复盘沉淀 | 横扫五通道，更新控制规则 |

## 8. 落地纪律（防本模型自己变成失控源）

- **别整份当 always-on**：它是参照 / 模板，不是每任务点火的规则；否则它就成了它反对的"规则压力集中"。新项目里按需 `manual`，或只把 §0 速用 + 硬规则设为常驻。
- **按项目阶段裁剪**：恢复轴、机械触发器都随项目实际副作用与规模增长再补，不提前建。
- **它定位控制点，不打分**：通道非等权、非独立、会相互放大。
- **不与项目既有 steering 抢职责**：模块边界、事实口径、外部合同、语言细则仍以项目自身对应文件为准；本模型只管"决策权在哪泄漏、如何交还、如何恢复"。
