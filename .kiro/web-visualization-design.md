# Web 可视化界面设计判断透镜

本文是做 Web 可视化界面设计时的**判断透镜与检查清单**，不是方法论文章，也不是任何项目的产品事实。十个维度是「设计时该从哪些角度想」的坐标，不是每个任务都要逐维走的关卡；小改动直接做。

**权威关系（别接反）**：门面稳定原则（纯渲染层、不新增判断、契约镜像、缺失如实）、契约字段与端点边界以**项目自己的产品/门面文档**为准；前端编码判断（组件/状态/类型/可访问性/测试）以 `frontend-console.md` 为准；某增量的组件、字段映射、界面验收以该增量的 spec/design 为准。本文只补上面未覆盖的**上游设计思考角度**，不复述其条款。

核心判断：**Web 可视化界面设计不是把后端字段摆上页面、也不是只做好看的 UI；它是从「谁在什么处境要完成什么任务」出发，经信息架构、交互、数据表达和视觉层级，把复杂能力变成用户能理解、能操作、能信任、能交接的工作环境。先定「为什么做、谁用、要完成什么、围绕什么对象」，再谈放什么卡片和图表——顺序反了，页面就会退化成字段与组件的堆叠。**

## 一、作用域：先问这套框架对当前对象成不成立

应用任何「正确原则」前先问它的作用域——对谁、在什么场景成立。若系统的**判断在后端/服务层成立**（如健康等级、严重程度、原因分类、优先级、指标口径、阈值来源、脱敏范围由后端裁决），则：

- 框架里「产品战略 / 数据可视化口径 / 结论信息架构」这些**判断维度的裁决权在后端，不在前端渲染层**；
- 前端作用域是**呈现与操作**：信息如何呈现与被找到、交互如何连续完成、数据如何在**不新增判断**的前提下表达、视觉层级如何服务任务、异常与缺失如何如实呈现、结果如何交接；
- 一句话边界：把框架里的「判断」维度读成「后端已给出的判断，前端如何忠实呈现并支持操作」。凡改变了使用者对结果的结论（隐藏、重排、补值、替后端判范围）就越线；只改变像素如何、何时出现，才是门面本职。

（若你的系统前端也承担判断，则相应维度的裁决权在前端，此节按实际归属调整。）

## 二、总体框架（从战略推到实现，不从卡片起步）

```text
产品战略与业务目标
→ 用户与使用场景
→ 用户任务与产品对象
→ 信息架构 IA
→ 用户体验 UX
→ 交互设计 IxD
→ 数据可视化设计
→ 用户界面 UI
→ 服务与协作设计
→ 技术实现与非功能要求
→ 产品验证与持续迭代
```

UI 只是其中一层，不是整个设计。上游没想清就先画页面，是最常见的返工来源。

## 三、十个设计维度（透镜）

| 维度 | 核心问题 | 关键产物 |
|---|---|---|
| 1. 产品战略与商业价值 | 为什么建这个界面？要改变什么组织结果？ | 产品目标、价值主张、成功指标 |
| 2. 用户与场景 | 谁在什么环境、什么压力下用？ | 用户角色、场景、用户旅程 |
| 3. 用户任务与产品对象 | 用户真正要完成什么？操作哪个对象？ | 任务链、对象模型、生命周期 |
| 4. 信息架构 IA | 信息怎么分类、分层、导航、检索？ | 站点结构、页面层级、导航体系 |
| 5. 用户体验 UX | 用户用前用后，认知与心理如何变化？ | 体验目标、关键路径、异常体验 |
| 6. 交互设计 IxD | 用户与系统如何连续完成复杂任务？ | 交互流程、状态反馈、操作规则 |
| 7. 数据可视化 | 数据如何帮助判断，而非制造噪音？ | 图表方案、指标口径、下钻关系 |
| 8. 用户界面 UI | 信息以什么视觉层级和组件呈现？ | 布局、组件、色彩、字体、视觉规范 |
| 9. 服务与组织协作 | 结果如何转交、复核、审批、留痕？ | 角色流程、权限、导出、协作机制 |
| 10. 技术与验证 | 是否可靠、快、安全、易维护？效果成立吗？ | 技术约束、验收指标、用户测试 |

每个维度的落地要点与最易做偏处：

1. **战略**：先答「解决什么真实问题、现有替代方式的成本、谁用谁受益谁付费、怎样算成立」，再谈做成什么样。（若此层已在项目产品文档成立，前端设计据其派生，不另立目标。）
2. **用户与场景**：To B 的「用户」是一组角色（操作者 → 复核者 → 决策者 → 执行者 → 管理者 → 审计/交付）。先分清谁操作、谁用结果、谁复核、谁担后果，以及用户是否处在告警/值班/汇报压力下。
3. **任务与对象**：从任务而非后端字段出发——用户要判断什么、操作什么对象、对象处于什么状态、如何流转、何时算完成。对象不清，页面必退化成字段堆叠。
4. **信息架构**：按用户任务/决策路径组织（我处理的对象 → 当前状态 → 风险异常 → 证据原因 → 下一步 → 历史交接），不按后端模块组织。自检：用户知道自己在哪、下一步去哪、关键内容是否在最短路径内、同一信息是否多处重复维护。
5. **UX**：设计心理状态迁移（不确定 → 确认 → 理解 → 信任 → 行动 → 完成）。**必须覆盖非 happy path**：空、加载中、部分成功、数据缺失、无权限、对象不存在、网络异常、结果过期、服务降级、操作失败。只设计顺路径不算完整 UX。
6. **IxD**：操作触发（何时点、哪些自动、哪些需二次确认、哪些不可逆）；状态反馈（已接收/处理中/部分完成/完成/失败/取消，长任务不能只转圈）；渐进披露（结论 → 风险 → 证据 → 技术详情 → 原始数据）；防错与恢复（可撤销、保留已填、防重复提交）；熟手效率（快捷键、批量、默认值、保存视图、快速筛选）。
7. **数据可视化**：先问用户要判断状态/趋势/分布/比较/关系还是异常，再选表达。**每张图必须说明单位、时间范围、更新时间、正常参照、阈值来源、缺失与异常值、是否可下钻。**不能帮用户形成判断或采取行动的图，就质疑它是否该出现。（若口径与阈值来自后端，前端只选忠实的表达形式，不自造指标或阈值。）

   | 判断目的 | 适合表达 |
   |---|---|
   | 当前状态 | 状态标签、数字卡、进度条 |
   | 时间趋势 | 折线图、面积图 |
   | 对象比较 | 条形图、表格 |
   | 构成关系 | 堆叠图、分组条形图 |
   | 分布与离群 | 箱线图、散点图 |
   | 拓扑与依赖 | 拓扑图、关系图 |
   | 风险定位 | 热力图、状态矩阵 |
   | 事件顺序 | 时间线 |

8. **UI**：核心是视觉层级——用户第一眼看什么、第二眼看什么、要操作时看什么、要核实时看什么。原则：结论优先于明细；状态颜色语义统一且颜色不作唯一载体（配文字/图标）；同类操作位置样式一致；页面密度匹配角色；不用装饰堆虚假高级感，也不把真实能力藏进无感页面。
9. **服务与协作**：To B 不止「一个人点页面」，还要设计结果如何进组织流程——谁发起/查看/复核/执行/审批/接收通知/反馈/留痕/负最终责任。很多看似 UI 的需求（如「导出报告」）其实是服务设计。（若对外交付物在后端拼装，前端不越脱敏、不在前端组装交付物。）
10. **技术与验证**：不能假设数据永远完整、接口永远快、状态永远一致——顾及加载性能、大数据渲染、前后端契约、实时更新、并发、错误处理、安全、权限、脱敏、审计、兼容、响应式、可访问性、可观测性。验证不能只看「页面完成/接口联通/组件齐全/截图相似/测试通过」，还要验证用户能否完成任务、多快、是否误操作、能否找到关键内容、是否知道下一步、是否愿重复用、能否完成交接。

## 四、四条横切原则

1. **UCD——用户事实约束设计**：用户价值判断要基于真实用户、任务、环境、使用验证，不靠团队想象。
2. **BTU——用户/商业/技术同时成立**：能否完成任务、是否可持续产生价值、能否可靠安全可维护地实现，缺一圈不成熟。
3. **Trust——高风险系统显式设计信任**：对 AI、金融、生产运维类系统，显式展示数据来源、新鲜度、结论依据、不确定性、缺失信息、责任边界、审计记录、降级状态。
4. **Accessibility——不同能力用户都可用**：键盘操作、对比度、字号、屏幕阅读器、色盲、图标配文字、错误提示、触控区域、多语言与术语理解。（编码级条款见 `frontend-console.md`。）

## 五、简化设计检查顺序

```text
1. 为什么做？      要改善什么用户或组织结果？
2. 谁来用？        在什么环境和压力下使用？
3. 要完成什么任务？ 任务结束的标准是什么？
4. 围绕什么对象？   对象有哪些状态和生命周期？
5. 信息怎么组织？   用户如何找到、理解、定位信息？
6. 如何交互？      用户和系统如何连续完成任务？
7. 数据如何表达？   哪些数据真正帮助判断？
8. 界面怎么呈现？   视觉层级、组件、布局如何服务任务？
9. 如何进组织流程？ 如何分享、交接、复核、留痕？
10. 如何验证？      用户是否真的更快、更准、更愿意使用？
```

答不清前四问，就不要先定组件和图表。

## 不做

- 不把十个维度当「必须逐项填满」的模板——它是判断坐标，简单界面直接做。
- 若前端是纯渲染门面，不用这套框架的「判断维度」给前端授权新增判断（重判等级/优先级、重排后端结论、给缺字段补默认值）——那越过门面边界。
- 不在缺少真实用户与任务事实时，先堆图表、先定视觉规范或先造通用配置化设计系统。
- 不引入与本栈无关的设计规范（跨产品设计令牌体系、他框架 UI 规则）当结论；需要时留通用参考，不写进落地设计。
