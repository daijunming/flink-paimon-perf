# 项目代码组织准则

本文件约束如何放置代码、划分模块、命名对象、管理依赖、记录决策和控制维护成本。它既给放置背后的第一性原理和判断透镜，也给可直接照做的操作规则。项目的模块职责、依赖方向、命名事实以**项目自己的结构文档**为准；边界、依赖方向、状态建模的设计检查与 `software-design-principles.md` 配合。

核心判断：**源文件分组的目的不是目录整齐，而是在「认知有限、未来变化不可完全预测、协作有成本」的条件下，让维护者和 Agent 能"安全地少理解一些"，并把变化尽量约束在局部。** 目录只是知识、变化、依赖、责任关系的**有损投影和认知提示，不是架构边界本身**——边界是否真正成立，取决于接口、依赖方向、可见性、构建、测试和责任制度。

## 分组在优化什么（先建立判断透镜）

分组要降低的是一次变更的长期成本。决定放哪时，在心里过这条成本链，而不是问"它属于哪一类"：

```text
定位 + 认知装载 + 跨界穿越 + 修改 + 验证 + 协调 + 迁移
  + 建立/维护结构的成本
  + 目录含义与真实关系脱节的漂移成本
```

这条成本来自四个不可消除的约束（不承认它们，任何目录规则都退化成审美偏好）：认知有限（人只能同时处理少量组块）、只能局部维护（需要"有条件的可忽略性"：当前任务大致在某边界内，边界外只需通过明确接口理解）、价值在持续变化中（分组是对未来变化分布的假设，不是对当前代码的分类）、技术依赖产生协调成本（Conway：目录让所有权和跨界修改可见）。

由此几条反直觉判断，遇到结构决策时优先自查：

- 目录不是越多越好：更细的目录降低某类定位成本，同时抬高导航、重构、结构维护成本。
- "看着整齐"未必成本最低：若高频变更总横穿所有目录，说明分组维度和真实变化维度不一致。
- 小项目、短期脚本不该上复杂结构：未来变更有限，结构投入收不回。
- 错边界比暂时无边界更贵：错目录制造错误推断、吸引错误依赖、抬高后续拆除成本。

## 1. 先建立与本次变更相关的最小项目地图

修改前至少看清：目标模块及其公共入口、一两个最接近的既有实现、目标模块的测试组织、直接上下游依赖、项目结构文档的对应部分；涉及文件移动时再查构建、配置、动态注册和文档引用。不要只搜到一个文件就改，也不要无目的遍历整个仓库。

## 2. 新增文件前先回答

先按变更级别分流，决定要答多少：

- **L0** 只改现有文件内部实现、不动文件树/依赖/公共接口 → 本文件不适用，照常改。
- **L1** 在既有模块内新增叶子文件、且有明确同类邻居 → 照邻居的位置、命名和测试办，不必逐条回答下面八问。
- **L2 / L3** 新建目录、移动文件、加公共入口、改依赖方向或新建顶层模块 → 动手前逐条回答下面八问并显式说明边界。

先识别变化原因，再决定目录名：什么会导致它变化？谁会与它共同变化？哪类知识要被隐藏？不要先造 `services`/`managers`/`common` 再往里塞文件。然后回答：

```text
它承载什么稳定职责与知识？
它会因什么原因变化？哪些现有文件会与它共同变化？
为什么不能放在已有位置？
谁调用它？它应该依赖谁？有没有禁止方向？
它和现有模块边界是什么？对外入口是什么？
如何独立验证它仍然正确？
未来下线能否整体删除？
是否需要同步测试、配置、文档或 ADR？
```

禁止为当前补丁随手创建 `utils`、`common`、`helpers`、`core`、`shared`、`manager`、`processor`、`handler`。确需使用时，先定义放什么、不放什么、谁能调用、谁不能调用。

对 Agent 尤其重要：默认目标偏向"找到代码、改完、测试绿、交付"，文件放在仓库根也能过测，当前任务不会惩罚错误放置，成本由后续维护者付。因此**"文件放置正确"是完成条件，不是编译/测试通过后的附带项**（与 `work-deviation-triggers` 的代理指标陷阱同源：测试绿是代理，可维护、放置正确才是真实目标）。

## 3. 目录应当像地图

目录主轴以项目结构文档规定的职责边界为准，不要在同一层同时堆叠多个分类维度（别造出 `stateful/`、`sync/`、`high-change/` 这种目录）。需要判断新边界时，按优先级取一条主轴：

1. 已知硬边界：外部协议、安全与权限、数据持久化、独立部署、第三方 SDK、跨网络调用、生成代码与人工代码；
2. 稳定知识边界：业务能力、主题域、数据责任、生命周期；
3. 依赖边界：核心接口与适配器、公共入口与内部实现；
4. 制品组织：测试、配置、脚本、文档按项目既有约定共置或镜像；
5. 变化频率、共同提交只作证据，不直接作目录名。

判断接缝的准则是共同变化：**共同变化的代码放近，独立变化的知识隔离**。"共同变化"不止同一次提交，还包括同一外部协议、同一业务规则、同一数据模型、同一失效模式、同一监管要求、同一运行生命周期。（反例：某外部协议的适配变化与某业务判定规则的变化，即便都与同一功能相关，变化原因不同，就不能只因"都和它有关"并进一个模块。历史共同变更是证据不是答案，需判断原因，别机械按提交历史聚类。）

时机上：已知硬边界（上面第 1 类）从一开始就建最低隔离；推测性细分（缺变化证据的细粒度层级、为假想复用建的共享抽象、无独立责任的顶层目录、只为对称而建的空目录）延迟固化——但延迟不等于先全平铺到乱。

找不到真实接缝时，不为显得有结构而拆目录。目录树只能表达一种主结构，是有损投影；依赖图、所有权、共同变更等其余关系用依赖检查、CODEOWNERS、测试目录、ADR、目录级 README 补充，别硬塞进一棵目录树。

## 4. 跨模块调用走明确入口

避免外部直接导入其他模块深层私有文件；工具层写入业务规则；核心层直接绑定外部 SDK；适配逻辑污染核心对象；测试 fixture 进入生产路径；配置、脚本、prompt、运行逻辑互相污染。

边界价值看**调用方为了正确使用它需要知道多少内部设计知识**，不看目录里有多少文件：三个文件的协议适配器可能隐藏极高价值的兼容知识；两百文件的"大领域模块"可能什么都没隐藏，因为调用方全知道它的库表和内部流程。

## 5. 命名保持统一语言

同一语义层内，一个工程对象只用一个主名称，不要让它在不同文件里叫 `case`、`record`、`item`、`snapshot`、`result`、`doc`、`data`。跨协议层、领域层、持久化层确实表达不同语义对象时可用不同名称，但要有显式映射，不因字段相似就强行统一，也不无理由地给同一对象堆近义名。

稳定的核心接口和领域对象按职责与业务能力命名，不绑定可替换实现；具体适配器和实现类应明确标出外部系统或技术绑定（如 `xxx_provider`、`xxx_client`），让"这是某外部系统的实现"一眼可见。

命名的第一性原理：**名字是系统对读者和调用方的语义承诺**——回答"这是什么稳定对象、承担什么能力、在哪个边界、被谁消费"，不是记录"来自哪个阶段、哪轮计划、哪次迁移"。阶段号、批次号、计划标签属于项目管理坐标、会随路线图变化，不进入运行时语义。若一个名字会因下一阶段到来而必须重命名，说明它绑的是临时过程，不是稳定概念。

## 6. 依赖就是风险

新增依赖前说明：解决什么问题；标准库或现有依赖能否满足；是否影响离线部署；是否影响版本兼容；是否有许可证或安全风险；是否需要 adapter 隔离；未来替换要改哪些地方。

数据库客户端、云 SDK、模型 SDK、监控 SDK、消息队列 SDK 等重依赖不得扩散进核心逻辑。

## 7. 决策需要留痕

涉及架构边界、核心数据模型、关键依赖、重要接口、放弃候选方案、现场约束下的长期妥协，或影响部署/排障/扩展/迁移的选择时，需要 ADR 或等价记录。记录背景、约束、候选方案、选择理由、放弃方案、代价和后续影响。

## 8. 追求易删性

新增能力要考虑下线成本：入口是否集中，配置是否集中，调用方是否清楚，测试是否独立，文档能否同步删除，数据迁移或状态清理是否清楚。无法干净删除，通常说明边界已经污染。

## 9. 修改后报告结构影响

说明是否改变目录结构、模块边界、外部依赖、命名体系；是否需要 ADR；是否有遗留腐化点；已执行了哪些验证命令、结果如何，以及未执行的验证及原因。

结束前过一遍"代码树差异"：是否新增孤立文件或模糊新目录（含万能名）？是否把领域知识塞进公共工具层？是否新增不必要的跨目录依赖或绕过公共入口？是否让目录名与实际责任发生偏差？**虚假整洁比明显混乱更危险**，因为它让后续维护者基于错误假设行动。

## 10. 结构风险信号（新建或扩大时暂停，别借题重构）

以下结构在**新建或继续扩大**时必须暂停并重新说明理由。若问题来自既有代码，不要借当前任务做无关的大范围重构——不扩大违规范围，完成当前任务后在结构影响里报告结构债务即可。

- 纯技术角色分组（`controllers`/`services`/`repositories`/`models`）把一个完整变化拆散：一个需求要在四个目录找同一业务对象。小应用或强框架下可接受；大型业务系统应在领域内部保留技术层，而非让技术层做全项目唯一顶层轴。
- 无边界的领域大目录：领域名对了，但内部无子责任、无公共入口、无依赖方向、无局部测试。
- `utils`/`common`/`shared` 垃圾场：唯一共同点是"多处在用"，没有共同变化原因。给不出比 `utils` 更准的名字，通常说明还没形成真正抽象边界。
- 过深层级：删掉某层后维护者对文件含义的预测几乎不变，说明该层没有信息价值。
- 虚假边界：目录看似隔离、依赖任意穿透，比平铺更危险；边界至少要有一种可验证机制兜底（依赖规则、可见性、构建、契约测试、所有权、独立验证入口）。
- 把执行顺序当模块结构（`step1`/`step2`/`step3`）：顺序易变且容易塞多份责任；用编排代码表达顺序，用目录表达稳定知识（按采集 / 规则 / 外部适配 / 专家判断等知识边界命名，不是步骤号）。

## 11. 移动、重命名、删除文件

移动或删除比新增风险更高，动手前先找全引用，别只改静态 import：静态 import、包声明、`__all__` 和公共导出；动态引用（字符串导入、反射、插件/Provider 注册、序列化类名、entry_points）；配置、资源路径、脚本、CI、容器构建里的路径；文档、示例、测试 fixture、运维命令里的路径；是否有外部调用方依赖旧路径，需要兼容转发层或弃用周期。

能移动就不要复制一份长期并存两套实现；生成文件改生成器 / Schema，不手工重排。完成后搜索旧路径与旧符号、跑构建与相关测试。
