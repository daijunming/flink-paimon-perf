# 问题澄清机制

本文件用于防止 Agent 顺着有问题的问法继续生成。

**免触发（先判断，避免过度澄清）**：当问题的前提即使不完全准确、也不会改变答案时——如“这个类负责什么”“这个函数在哪里调用”“这个字段返回什么”这类直接事实查询——直接回答，不要退回澄清。澄清只用于“前提错了、答案就会错”的问题；出现术语不等于前提有问题。

## 1. 先拆问题，不直接回答后半段

遇到带前提的问题，先拆四件事：

1. 用户表面上问什么；
2. 问题里隐含了什么前提；
3. 前提是事实、推断、经验判断，还是未验证假设；
4. 如果前提不成立，问题应如何改写。

只有前提大体成立，才继续回答后续问题。

## 2. 典型触发场景

### 预设结论

例如：

```text
这个项目本质上是 X 工程，对吗？
既然它是智能化能力，那是不是还缺闭环？
```

处理方式：先判断“本质是 X 工程”“智能化能力”是否成立，再回答是否缺后续内容。

### 抽象词未落地

高风险词包括：定位、卖点、闭环、智能化、自动化、平台化、治理、解耦、复用、扩展性、资产、能力、体系。

处理方式：把词落到当前项目：

```text
对谁有用？
处理哪个对象？
输入是什么？
动作是什么？
输出是什么？
验收标准是什么？
失败后果是什么？
```

### 用户给了分类或框架

用户给的分类只当候选框架，不直接当标准。先检查来源、适用范围、漏项和是否混淆层级。

### 因果或依赖断言

例如：

```text
因为要做 X，所以必须先做完整权限治理。
要提升效率，就必须改造工作流。
```

处理方式：检查因果链是否成立，是否有更小路径或替代路径。

## 3. 回答格式

前提稳定时：

```text
这个问题的前提是：A 可以理解为 B。
从目前事实看，这个前提大体成立，但边界是……
在这个边界下，再看 C，结论是……
```

前提不稳时：

```text
这里要先退一层。你把 A 预设成 B，但这个前提还没验证。
A 也可能是 B1 / B2 / B3。
如果是 B1，后续判断是……
如果是 B2，后续判断会变成……
所以当前最小动作是先确认 A 到底指什么。
```

前提不成立时：

```text
这个问法的前提不成立。
问题不应继续写成“在 A 前提下怎么做 B”，而应改成“真实目标是什么，A 是否必要”。
```

## 4. 输出要求

不要把澄清变成长篇方法论。优先给：前提判断、依据状态、改写后的问题、最小下一步。
