# Paimon 写入与合并性能分析指导(现场形态)

> 面向运维/分析人员的操作手册:写入作业(write-only)与独立合并作业(crontab 批任务)
> 各自"干得怎么样"该看哪里、怎么判读。
> 事实基础:2026-08-06 与现场实际运行形态核对;`06_compaction_job.sh` 已对齐该形态,
> 2026-08-11 加入 flock 防重入(上一轮未结束本轮跳过)并同步现场资源参数。

## 一、真实作业形态(一切分析口径的前提)

| 作业 | 形态 | 关键配置 |
|------|------|----------|
| 写入 `DataStreamperf_paimon` | 常驻流作业,write-only,**只写不合** | bucket=512 / parallelism=3,checkpoint 间隔见 `job-run-params.json` |
| 合并 `paimon-compact` | **crontab 每 5 分钟提交一次 BATCH 任务**,跑完即退出 | `flink run-application -t yarn-application -Dexecution.runtime-mode=BATCH`,`paimon-flink-action compact --compact_strategy minor`,JM 2048m / TM 15360m / managed 0.1 / 3 slots |

合并任务现场实际 `--table-conf`(2026-08-06):`changelog-producer=lookup`、
`changelog-producer.row-deduplicate=true`、`lookup-compact=radical`、
`num-sorted-run.compaction-trigger=5`、`scan.split-enumerator.batch-size=1`、
`sink.use-managed-memory-allocator=true`、`sink.parallelism=3`、
`parquet.enable.dictionary=false`、`read.batch-size=512`。
`lookup-compact=radical` 负责在每次触发 Compaction 时推动 L0 向高层合并；Sorted Run 阈值保留
Paimon 1.1 默认值 5，用于控制 Universal Compaction 何时选择更大范围的候选集。

**两个直接推论(决定数据去哪看):**

1. 指标链路 3 分钟上报一批,而活几十秒的批任务大概率**一条 Flink 指标都进不了**
   `RDW_ODS_FLINK_METRICS`;且 `paimon-compact` 不在分析视图白名单(白名单里的
   `compaction_job` 是旧流式形态)。→ `metrics_compaction_job` 视图、
   `05_health_flags` 的 `compaction_flag` 在当前形态下**无数据**,compact 作业侧
   只能看 cron 日志和 YARN 应用历史。
2. 写入作业是常驻流,指标链路对它有效,作业侧照常用分析视图。

## 二、分析框架:两个对象 × 两条通路

| | 作业侧(指标/日志,回答"花了多少资源、忙不忙") | 表侧(元数据事实,回答"干的活有没有效果") |
|---|---|---|
| **写入** | `RDW_ODS_FLINK_METRICS` → analysis-sql 视图(有效) | `rdw_ods_paimon_meta_*`(meta-collect 采集) |
| **合并** | cron 日志 + YARN 历史(指标链路拿不到) | 同上(主通路) |

**效率 = 表侧产出 ÷ 作业侧投入**,单看一边都会误判。

表侧数据来源:`scripts/meta-collect/`(crontab 每 3 分钟批采集 Paimon 系统表 → Kafka →
StarRocks ODS 表,9 张 PRIMARY KEY 表,主键覆盖幂等)。这是**唯一的表侧通路**——
Java metadata-collector 已于 2026-08-11 现场退役,其聚合口径(L0–L5 文件数)只剩历史数据;
文件级差分本就只有本通路能做。

## 三、合并(compact)分析

### 3.1 作业侧

- **cron 日志**:`06_compaction_job.sh` 每轮记录起止/退出码/耗时(attached 模式,
  为作业真实结果),运行时长趋势 = 单次工作量曲线;出现"本轮跳过"= 上一轮超 5 分钟,
  合并实际频率减半,需放宽 cron 间隔或换增量策略。
- **YARN 应用历史**:按应用名 `paimon-compact` 查运行时长、容器资源占用、失败记录。

### 3.2 表侧即时核查(不等采集链路,直接执行)

```sql
-- 1) COMPACT 提交是否每 5 分钟产生(与 APPEND 交替,commit_user 区分来源)
SELECT snapshot_id, commit_kind, commit_time, commit_user, delta_record_count
FROM paimon_obs.paimon_database.`wide_table$snapshots`
ORDER BY snapshot_id DESC LIMIT 20;

-- 2) 单次 compact 干了多少活:manifest 的增删文件数(前后 snapshot 对比)
SELECT SUM(num_added_files) AS added, SUM(num_deleted_files) AS deleted
FROM paimon_obs.paimon_database.`wide_table$manifests`;

-- 3) L0 是否收敛(Minor 不要求单轮清零；需要观察多轮数量、字节数和最老文件年龄)
SELECT level, COUNT(*) AS file_count, SUM(file_size_in_bytes) AS bytes
FROM paimon_obs.paimon_database.`wide_table$files`
GROUP BY level ORDER BY level;

-- 4) 最老 L0 文件年龄：超过多个 5 分钟调度周期，才是未被处理的直接证据
SELECT MIN(creation_time) AS oldest_l0_creation_time,
       TIMESTAMPDIFF(SECOND, MIN(creation_time), CURRENT_TIMESTAMP) AS oldest_l0_age_sec
FROM paimon_obs.paimon_database.`wide_table$files`
WHERE level = 0;
```

```bash
# 5) 磁盘占用拆解(总量 vs 当前有效数据)
hdfs dfs -du -s -h ${PAIMON_WAREHOUSE}/paimon_database.db/wide_table
hdfs dfs -du -h   ${PAIMON_WAREHOUSE}/paimon_database.db/wide_table   # 按 bucket-*/manifest/snapshot 子目录展开
```

`du` 总量 − `$files` 的 `SUM(file_size_in_bytes)`(当前有效数据)= **历史包袱**,构成:
快照保留窗口内的旧文件 + compact 每轮生成的 changelog 文件(`changelog-producer=lookup`)
+ 可能的孤儿文件。对应动作:查 `$options` 的 `snapshot.time-retained` /
`snapshot.num-retained.*`(保留窗口直接决定包袱厚度);孤儿文件用 paimon action
`remove_orphan_files` 清理。

### 3.3 持续观测(meta-collect ODS 表)

```sql
-- COMPACT 节奏:5 分钟周期是否发生、有无断档
SELECT snapshot_id, commit_time,
       TIMESTAMPDIFF(SECOND, LAG(commit_time) OVER (ORDER BY snapshot_id), commit_time) AS gap_seconds
FROM rdw_ods_paimon_meta_snapshots
WHERE table_name='wide_table' AND commit_kind='COMPACT'
ORDER BY snapshot_id DESC LIMIT 30;

-- 单次 compact 实际替换文件数(N=前, M=后;added≈0 且 removed≈0 = 空转)
WITH prev AS (SELECT file_path FROM rdw_ods_paimon_meta_files
              WHERE table_name='wide_table' AND source_snapshot_id=<N>),
     cur  AS (SELECT file_path FROM rdw_ods_paimon_meta_files
              WHERE table_name='wide_table' AND source_snapshot_id=<M>)
SELECT
  (SELECT COUNT(*) FROM cur  LEFT JOIN prev USING(file_path) WHERE prev.file_path IS NULL) AS files_added,
  (SELECT COUNT(*) FROM prev LEFT JOIN cur  USING(file_path) WHERE cur.file_path  IS NULL) AS files_removed;

-- L0 是否被压住(Minor 的核心职责；结合最老 L0 文件年龄判断是否跨多轮滞留)
SELECT source_snapshot_id, level, file_count, file_size_in_bytes
FROM v_paimon_meta_level_stats
WHERE table_name='wide_table' AND level=0 ORDER BY source_snapshot_id;

SELECT source_snapshot_id,
       MIN(creation_time) AS oldest_l0_creation_time,
       TIMESTAMPDIFF(SECOND, MIN(creation_time), MAX(collected_at)) AS oldest_l0_age_sec
FROM rdw_ods_paimon_meta_files
WHERE table_name='wide_table' AND level=0
GROUP BY source_snapshot_id ORDER BY source_snapshot_id;

-- 文件大小分布与有效体积演进(total_bytes 对比 du 总量 → 膨胀率)
SELECT source_snapshot_id, file_count, total_bytes, p50_bytes, p90_bytes
FROM v_paimon_meta_file_size_stats
WHERE table_name='wide_table' ORDER BY source_snapshot_id;
```

### 3.4 判读

- **"几十秒跑完"**：Minor 只处理命中条件的 Sorted Run，耗时低于原 Full 是预期结果。
  不能只看耗时判断是否有效；要结合 cron/YARN 成功记录、COMPACT Snapshot、文件替换和
  L0 数量/字节/最老文件年龄。某轮无 COMPACT 提交也可能是没有候选文件，不能单独判作没运行。
- **磁盘 389GB 类膨胀**:先看"有效数据 vs 总占用"的比例。包袱为主 → 调 retention 窗口、
  清孤儿文件;有效数据为主 → 磁盘规划问题,不是清理问题。

## 四、写入任务性能与写入效率分析

### 4.1 作业侧(现有分析视图,常驻流作业指标有效)

| 看什么 | 在哪看 | 判读 |
|--------|--------|------|
| 吞吐 `write_rps` | `05_health_flags.sql` | 与 SLA 20000 条/秒对照;窗口平均速率,已处理上报缺口 |
| 背压 `backpressure_flag` | `05_health_flags.sql` | >30s/分钟即标志;write-only 主键表瓶颈通常表现为 sink 背压 |
| Snapshot 提交节奏 | `08_checkpoint_health.sql` | 只能看到 Snapshot 是否推进及提交间隔；当前视图混合写入与 COMPACT 提交，不能据此还原 checkpoint 耗时、失败次数或事件到流读输出的端到端延迟 |
| YARN/HDFS 资源 | 已退役(resource-collector 2026-08-11 停止运行,`metrics_resource_compaction` 视图已删除),无替代通路 | 只能看 YARN/HDFS 自带 UI/CLI |

### 4.2 表侧印证(ODS 通路)

- **实际落表速率**:`rdw_ods_paimon_meta_snapshots` 的 APPEND 提交节奏 ×
  `delta_record_count`,与 `write_rps` 互验(指标链路断时也能从快照还原)。
- **L0 产出速率**:`rdw_ods_paimon_meta_files` 中 level=0 的字节/数量增量——写入给
  compact 制造的压力;L0 产出与 compact 清理量之差 = 磁盘净增长。
- **写入均衡**:`rdw_ods_paimon_meta_buckets` 512 个 Bucket 的增量分布是否均匀——hash 倾斜会让单个
  writer subtask 成为瓶颈。
- **逻辑行数**:snapshots 表 `total_record_count` 曲线——3000 万账户、50% update
  场景下应贴着 3000 万缓涨;快速上涨说明 insert 占比异常(生成器配置问题)。

### 4.3 瓶颈判读组合

| 现象组合 | 结论 | 下一步 |
|----------|------|--------|
| 摄入不达标 + sink 背压高 | Paimon 写入链路存在压力 | 看 L0 积压、Snapshot 提交节奏，并从 Flink/YARN 原始运行记录补查 checkpoint 与资源指标 |
| 背压低但吞吐不达标 | 上游问题 | 查 Kafka 消费滞后、生成器限速配置 |
| Snapshot 提交间隔拉长 | 写入提交或作业运行可能异常，现有数据不能单独归因 | 先按 `commit_user`/`commit_kind` 分离写入与 COMPACT，再补查 checkpoint 历史和 manifest 规模 |
| 单 bucket 增量显著高于其他 | 主键 hash 倾斜 | 对应 subtask 忙闲不均,评估 bucket 数 |
| write_rps 高 + L0 持续积压 + compact 每轮增删≈0 | 写得快、合不动(空转) | 按 3.4 处理合并侧 |

## 五、配置观测注意

`$options`(及 ODS `rdw_ods_paimon_meta_options` 表)只含**建表 DDL 持久化**的配置
(如 `bucket=512`、`changelog-producer=lookup`、`write-only=true`),看不到 Action 运行时的
内存、并行度和读取批次。分析配置时以"DDL + 各作业启动参数"两边为准。

## 七、三个任务的事后分析边界

当前数据与脚本只能做**部分事后分析**，不能完整还原写入、Minor 合并、流式读取三个任务的性能。

| 任务 | 当前能复核 | 当前不能复核 | 判定 |
|------|------------|--------------|------|
| 写入 `DataStreamperf_paimon` | 处理吞吐、已上报的背压/忙碌度、checkpoint start delay、Snapshot 提交记录、文件与 Bucket 分布 | 完整 checkpoint 耗时与失败、Kafka lag、CPU/Heap/GC/网络、事件写入可见延迟；累计计数跨作业重启也未按 `job_id` 断开 | 部分符合 |
| 合并 `paimon-compact` | cron 日志保留时可看每轮起止/退出码；表侧可看 COMPACT Snapshot、L0 数量/字节/最老文件年龄、文件尺寸与 Bucket 分布 | 作业级 CPU/Heap/GC/网络/读写字节、单 Bucket 耗时、每轮实际输入输出文件；3 分钟元数据采样也会漏掉采样间隔内的中间文件状态 | 部分符合 |
| 流读 `streaming_read_job` | 指标实际存在时可看输出吞吐、背压与忙碌度 | Snapshot 消费滞后、事件到流读输出延迟、结果正确性；当前任务没有 `consumer-id`，`$consumers` 无法提供该任务的消费位置 | 部分符合 |

`metrics_read_vs_write` 当前不能把 `write_total - read_total` 解释为流读积压：lookup Changelog
对一次 UPDATE 可能输出 `-U/+U`，也可能因 row-deduplicate 不输出，写入记录数与流读 Changelog
记录数不是同一计数口径；流读默认还会先读取启动时已有的全量 Snapshot。该视图只能展示两个速率，不能用于
判定消费是否追上。

要达到“完整事后分析三个任务”的标准，至少还缺三组证据：

1. 写入任务按 `job_id` 分段的 checkpoint、Kafka lag 与 JVM/资源历史；
2. 每轮 `paimon-compact` 的 run_id、实际运行参数、作业资源指标及输入/输出文件统计；
3. 流读任务稳定的 `consumer-id` 消费位置，以及基于 `event_time` 产生的端到端延迟指标。
