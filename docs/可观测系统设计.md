# Flink + Paimon 任务可观测系统设计（采集 / 分析 / 治理）

> 模块设计文档。以仓库现状为事实基础：标注【已建】的为现场可复核通路，标注【缺口】/【规划】
> 的为尚未实现部分。现场演进日期见各条目；推进路径类文档见 `docs/README.md` 导读。

## 一、目标与观测对象

对三类任务提供"采集 → 分析 → 治理"闭环，支撑 SLA 判定（写入吞吐 ≥ 20000 条/秒、
端到端延迟 ≤ 3 分钟）与瓶颈定位：

| 任务 | 作业名/载体 | 形态 |
|------|------------|------|
| 写入 | `DataStreamperf_paimon`（平台 STREAMING 作业） | 常驻流，write-only 只写不合 |
| 治理（合并） | `paimon-compact`（`scripts/sql/06_compaction_job.sh`） | crontab 批任务，每 5 分钟一轮，几十秒退出 |
| 读取 | `streaming_read_job`（`scripts/sql/07_streaming_read.sql`） | 常驻流，blackhole sink |

## 二、设计原则（全系统通用，违反即返工）

1. **事实与判断分离**：ODS 层只存可复核事实（位移、文件数、字节数），"是否健康/是否达标"
   一律由分析层计算。判断口径改十版，采集侧不用动。
2. **幂等可重放**：SR 全部 PRIMARY KEY 表，重复采集/重发/重叠轮次 = 主键覆盖；
   采集脚本无本地游标，任意一轮失败等下一轮自愈。
3. **失败隔离**：单轮失败不中断后续轮次；多路采集互不影响；Kafka 写入失败时事实落日志不丢。
4. **采集周期匹配被采对象生命周期**：批任务几十秒 < 指标上报周期 3 分钟，
   批任务侧一律看 cron 日志/YARN 历史，不指望指标链路（查不到 ≠ 没跑）。
5. **任务级指标聚合纪律**：桶内 MAX → 单算子内跨 subtask SUM → 跨算子 MAX 去重 →
   相邻差分 ÷ 实际间隔秒。第三层不可省：任务级链名与算子级名双粒度重复上报、计数相同
   （2026-08-12 现场核实），不分算子直接 SUM 吞吐虚高约 2 倍。
6. **双口径互验**：作业侧指标、表侧元数据、链路侧位移三方对得上才下结论。

## 三、总体架构

```
┌─────────────── 采集层（crontab / 常驻链路，只产事实）───────────────┐
│ ① 作业指标:既有 Flink 链路(3 分钟/批)                              │
│ ② 表侧元数据:collect_once.sh(*/3min,Flink SQL Batch 读系统表)      │
│ ③ 物理层:collect_physical.sh(*/10min,HDFS du/ls)                   │
│ ④ 链路侧:collect_kafka_offsets.sh(*/1min,topic 分区位移)           │
│ ⑤ 资源层:【缺口】YARN RM REST(规划)                                 │
│ ⑥ 生命周期:collect_runs 表 / compact cron 日志 / YARN 应用历史      │
└──────────────────────────┬───────────────────────────────────────┘
                           ↓ Kafka(topic 与 SR 表一一对应)
┌─────────────── 存储层（StarRocks）────────────────────────────────┐
│ Routine Load → ODS:rdw_ods_paimon_meta_*(10 张)+                  │
│ rdw_ods_kafka_topic_offsets + 既有 RDW_ODS_FLINK_METRICS          │
│ (全部 PRIMARY KEY,主键覆盖幂等)                                    │
└──────────────────────────┬───────────────────────────────────────┘
                           ↓
┌─────────────── 分析层（视图,查询时计算不落存储）───────────────────┐
│ analysis-sql:01 底座 / 02 四类指标 / 05 健康标志 / 08 快照健康 /     │
│ 09 流读与读写对照;meta-collect:level_stats / file_size_stats /      │
│ v_kafka_topic_write_rate;SLA 判定【缺口,03_sla_check 搁置】         │
└──────────────────────────┬───────────────────────────────────────┘
                           ↓
┌─────────────── 治理层（依据分析结论的动作）────────────────────────┐
│ 合并治理(06 脚本双防重)/ 生命周期(retention、孤儿清理)/ 容量(包袱   │
│ 拆解)/ 配置(options 变更追踪)/ 告警【缺口:无通知通道】/ 自愈【规划】 │
└──────────────────────────┬───────────────────────────────────────┘
                           ↓
┌─────────────── 呈现层 ────────────────────────────────────────────┐
│ 测试报告模板(已有)/ 仪表盘【缺口】/ 报告自动化【规划】               │
└───────────────────────────────────────────────────────────────────┘
```

| ⑥ | 作业生命周期 | 批任务起止/退出码/耗时；采集轮次成败 | `collect_runs` 表、06 cron 日志、YARN 应用历史 | 随任务 | 【已建】短命批任务的唯一可靠通路（原则 4） |

采集脚本统一约定：properties 配置 fail-fast、flock 防重入、Kerberos ticket 由 cron 用户保证、
渲染/临时产物有保留期自动清理（`RENDERED_RETENTION_DAYS`）。

## 五、存储层模块

- **缓冲**：Kafka 削峰，topic 名与 SR 表名一一对应，按域分不按业务表分（新增被监控表零建设）。
- **ODS**：StarRocks PRIMARY KEY 表；主键均含 catalog/database/table（物理/位移表按域含 topic）。
- **装载**：Routine Load（`03_routine_load.sql` / `04` / `05`，占位符 `${KAFKA_BOOTSTRAP_SERVERS}`）；
  若走既有 Flink 入库链路则按列名映射等价替代。
- **保留**：行级历史靠 SR 分区/TTL；Paimon 侧已过期的 Snapshot 行在 ODS 中保留，
  形成超出 `snapshot.time-retained` 的长历史。

## 八、两个薄弱维度的现状与补齐方案

- **数据时延**：真端到端时延从未采到（LatencyProbe 已移除，`ingest.e2e_latency_ms` 从未产出）。
  现状近似 = 快照提交间隔（可见性上界，checkpoint 3min 配置）。补齐按成本排序：
  ① `event_time` 新鲜度查询（表记录自带 epoch 毫秒，`NOW()*1000 - MAX(event_time)`，
  周期执行落 ODS 即可）；② 分解估算 = Kafka 排队 lag（待采）+ checkpoint 间隔（已有）；
  ③ 生成器哨兵探针 + 可见侧回读（最准，工作量最大）。
- **任务负载**：已有忙闲/反压时间占比（busy/backPressured/checkpointStartDelay）；
  CPU/Heap/GC/网络无通路。最低成本补齐：YARN RM REST per-app `vcoreSeconds`/`memorySeconds`
  累计值周期采集 + 差分（与 offsets 脚本同模式）；JVM 级需动指标上报链路，压测期不做。
