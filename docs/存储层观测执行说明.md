# 存储层观测执行说明

## 1. 文档目标

本文档只说明存储层观测的推荐执行路径、结果出口、部署边界与调度方式，不重新定义测试口径。

## 2. 结论先行

当前仓库不再把 `Flink SQL -> 直接查询 Iceberg metadata table` 作为表侧 metadata 指标采集主路径。

原因固定如下：

1. `Flink 1.19` 流式 SQL 对 `INSERT` 前 CTE、metadata table 投影裁剪与 planner 推断都不够稳
2. Iceberg metadata table 在当前环境里已经出现 `Row arity` 不匹配，说明这条链路本身不够可靠
3. 存储层观测是分钟级批式采样，不需要和主写入作业绑在同一条 Flink SQL 作业内
4. 平台已有 Flink metrics 上报 Kafka 能力，表侧 metadata 指标应接入同类 metrics Kafka 管道，再落 StarRocks 分析

结论固定为：

1. 主写入作业继续跑在 Flink `streaming`
2. 表侧 metadata 指标由独立采集执行器按分钟或阶段采样
3. 表侧 metadata 指标第一出口为平台 metrics Kafka，不直连业务 Kafka topic
4. StarRocks 负责 Kafka 下游落库后的归档、聚合、阶段对比与图表查询

## 3. 推荐架构

推荐链路如下：

1. 外部调度器每分钟触发表侧 metadata 采集执行器
2. 采集执行器在一个时间点读取 Paimon 与 Iceberg 的 metadata
3. 采集执行器将结果归一化成 metrics 事件
4. metrics 事件写入平台 metrics Kafka
5. 平台 Kafka 到 StarRocks 链路将指标落入分析表
6. 测试分析直接在 StarRocks 中完成

职责边界固定如下：

1. Flink 主作业只负责写业务表
2. 表侧 metadata 采集执行器只负责采 metadata 并产出 metrics 事件，不参与主链路计算
3. metrics Kafka 负责统一接收 Flink 运行态指标和表侧 metadata 指标
4. StarRocks 只负责观测结果存储与分析

## 4. 为什么不再推荐 Flink SQL 采 metadata

本仓库保留 `flink/observe_storage_metrics.sql`，但它只适合作为临时排查模板，不再作为主方案。

不再推荐的原因如下：

1. 这条脚本本质上是“一次采样、一次退出”，与流式 SQL 的长作业模型并不匹配
2. 当前问题不是单纯 SQL 写法问题，而是 planner 与 metadata table 的组合稳定性问题
3. 即使改成 view、子查询或显式 schema，也可能在优化阶段再次被裁剪
4. 这类问题会让观测链路本身成为噪音，反而影响对 Paimon 与 Iceberg 的结论判断

## 5. StarRocks 分析表设计

StarRocks 侧标准表结构见：

1. `starrocks/storage_metrics_ddl.sql`
2. `starrocks/storage_metrics_queries.sql`

Paimon 与 Iceberg 的详细观测参数见：

1. `docs/Paimon 观测监控参数说明.md`
2. `docs/Iceberg 观测监控参数说明.md`

表侧 metadata 指标使用平台表 `RDW_ODS_FLINK_METRICS` 的结构派生专用分析表，不直接复用 Flink metrics 原表。`rtp_observe.storage_metrics_snapshot` 与 `starrocks/storage_metrics_ddl.sql` 只保留为历史分析表候选，不作为采集端直写契约。

表侧 metadata 指标进入 metrics Kafka 时，最少应贴合平台字段：

1. `jobName`
2. `appId`
3. `jobId`
4. `hostName`
5. `containerId`
6. `containerRole`
7. `metricName`
8. `metricType`
9. `metricValue`
10. `metricTs`

其中 `jobName` 按平台规范承载 `engine` 与 `table_name`；`metricName` 只承载指标名称。`stage_label` 与 `database_name` 不进入表侧 metadata 指标事件。

## 6. 表侧 metadata 指标采集约束

当前选定 Spark 作业作为表侧 metadata 采集执行器，不再依赖 Flink SQL 流作业 planner，也不并行开发 Flink batch、平台任务或轻量 Java adapter。

约束固定如下：

1. 采集执行器每次只做单次快照采样，写完 metrics 事件即退出。
2. 指标事件必须符合平台 metrics Kafka JSON 报文形态。
3. 脚本名称即为写出的表或 topic 名称；作业名称必须包含 `engine` 与 `table_name`。
4. `stage_label`、`database_name` 不写入表侧 metadata 指标事件。
5. `engine`、`table_name` 不作为独立字段写入表侧 metadata 指标事件，只从 `jobName` 解析。
6. 所有环境地址、用户名、密码都通过外部参数或环境变量传入，不写入仓库。
7. 采集参数必须显式区分 Paimon catalog、Iceberg catalog 与 metrics Kafka 输出，不能把这些信息折叠成一段不可校验的 shell 字符串。
8. 业务 Kafka 连接信息只用于主测试链路的输入发布、消费 lag 与探针追踪；表侧 metadata 指标只写平台 metrics Kafka，不写业务 topic。

## 7. 指标事件与采集参数契约

后续采集执行器当前固定为 Spark 作业。Spark 作业必须产出可进入平台 metrics Kafka 的指标事件。本文只定义参数边界，不新增 YAML、JSON 或其他配置权威。

### 7.0 已确认的平台指标通道

平台 Flink metrics 已通过 Kafka 上报，表侧 metadata 指标应复用同类指标通道。已确认事实如下：

| 项目 | 确认值 | 说明 |
|---|---|---|
| metrics Kafka topic | `rdw_ods_flink_metrics` | 表侧 metadata 指标写入同一指标 topic |
| 事件格式 | JSON | 参考现有 Flink metrics 报文 |
| 认证 | 无 | 仍不得在仓库记录真实 broker |
| 分区键 | 指标名称 | 对应 JSON 字段 `metricName` 或等价字段 |
| 投递成功语义 | 至少一次 | 下游分析需要能识别重复或覆盖语义 |

现有 Flink metrics JSON 报文字段包括：`jobName`、`appId`、`jobId`、`hostName`、`containerId`、`containerRole`、`metricName`、`metricType`、`metricValue`、`metricTs`。

StarRocks 侧可参考平台表 `RDW_ODS_FLINK_METRICS`，其主要字段包括：`etl_dt`、`metric_id`、`job_name`、`app_id`、`job_id`、`host_name`、`container_id`、`container_role`、`metric_name`、`metric_type`、`metric_value`、`metric_ts`。

已确认表侧 metadata 指标不再输出独立 `stage_label`、`database_name`、`engine`、`table_name`。其中 `engine` 与 `table_name` 由平台作业名 `jobName` 承载，脚本名称遵循“脚本名称即写出表或 topic 名称”的平台规范。表侧 metadata 指标使用 `RDW_ODS_FLINK_METRICS` 结构派生专用分析表。`metric_id` 由 Kafka 到 StarRocks 落库链路生成，Spark 采集事件不携带该字段。

### 7.1 必选参数

| 参数 | 归属 | 含义 | 来源 |
|---|---|---|---|
| `--job-name` | 平台作业 | metrics Kafka 事件中的 `jobName`，必须包含 `engine` 与 `table_name` | 实时平台作业命名规范 |
| `--paimon-warehouse` | Paimon catalog | Paimon `warehouse` 原生参数 | 测试环境 Paimon catalog 配置 |
| `--paimon-database` | Paimon catalog | Paimon catalog 内数据库名；仅用于采样定位，不写入指标事件 | 测试方案或建表 SQL |
| `--iceberg-catalog-type` | Iceberg catalog | Iceberg `catalog-type` 原生参数，例如 `hadoop` | 测试环境 Iceberg catalog 配置 |
| `--iceberg-catalog-name` | Iceberg catalog | Iceberg `catalog-name` 原生参数 | 测试环境 Iceberg catalog 配置 |
| `--iceberg-warehouse` | Iceberg catalog | Iceberg `warehouse` 原生参数 | 测试环境 Iceberg catalog 配置 |
| `--iceberg-database` | Iceberg catalog | Iceberg catalog 内数据库名；仅用于采样定位，不写入指标事件 | 测试方案或建表 SQL |
| `--metrics-topic` | metrics Kafka | 平台确认的指标 topic，当前为 `rdw_ods_flink_metrics` | 平台指标规范 |
| `--metrics-format` | metrics Kafka | 平台确认的指标事件格式，当前为 `json` | 平台指标规范 |

说明：

1. Paimon 与 Iceberg 的 catalog 参数必须分开声明，不能合并为 `catalog`、`warehouse` 这类模糊参数。
2. 业务 Kafka 参数不属于 metadata 指标采集，不允许被混入采集参数；metrics Kafka 参数只表达平台指标通道。
3. StarRocks 用户名、密码、token 不应出现在采集命令示例中；StarRocks 连接由 Kafka 下游落库链路管理。
4. 采样对象由平台脚本名和作业名确定。若执行器内部仍需要表定位参数，应由执行环境按原生 catalog 口径注入，但不得作为表侧 metadata 指标事件字段输出。

### 7.2 可选参数

| 参数 | 含义 | 默认值 |
|---|---|---|
| `--metadata-source` | 采样实现来源 | `spark` |
| `--collector-run-id` | 调度侧采样批次编号，只用于日志追踪，不写入最小指标事件 | 空 |
| `--yarn-app-id` | 关联 YARN application id | 空 |
| `--fail-on-partial` | 任一表采样失败时整体失败 | `true` |
| `--dry-run` | 只打印采样计划与参数校验结果，不写 metrics Kafka | `false` |

### 7.3 参数校验

采集执行器启动时必须完成以下校验：

1. `--job-name` 不允许为空，并且必须符合平台命名规范，能识别 `engine` 与 `table_name`。
2. `--paimon-warehouse` 与 `--iceberg-warehouse` 不能互相复用。
3. `--iceberg-catalog-type` 必须与测试环境实际 catalog 类型一致。
4. `--metrics-topic` 必须为平台确认的 `rdw_ods_flink_metrics` 或平台后续确认的等价 topic，不能由本仓库临时发明。
5. `--metrics-format` 必须为平台确认的 `json` 或平台后续确认的等价格式。
6. 参数校验日志不得打印完整 Kafka 连接串、用户名、密码、token 或其他敏感值。

## 8. Metrics 事件到 StarRocks 字段映射

表侧 metadata 指标事件进入 metrics Kafka 后，由平台落库链路写入 StarRocks。当前平台表可参考 `RDW_ODS_FLINK_METRICS`，仓库内 `starrocks/storage_metrics_ddl.sql` 只保留为历史分析表候选，不作为当前采集端事件契约。

专用分析表从 `RDW_ODS_FLINK_METRICS` 参考结构派生。不再为表侧 metadata 指标新增独立 `stage_label`、`database_name`、`engine`、`table_name` 字段。`engine` 与 `table_name` 从 `job_name` 解析，`stage_label` 与 `database_name` 不进入指标事件。

参考映射如下：

| StarRocks 字段 | metrics JSON 字段 | 说明 |
|---|---|---|
| `etl_dt` | Kafka 到 StarRocks 落库链路生成 | 数据日期 |
| `metric_id` | Kafka 到 StarRocks 落库链路生成 | 指标主键；Spark 采集事件不携带该字段 |
| `job_name` | `jobName` | 作业名，必须包含 `engine` 与 `table_name` |
| `app_id` | `appId` | YARN application id |
| `job_id` | `jobId` | Flink job id 或采集运行 id，需确认 |
| `host_name` | `hostName` | 上报节点 |
| `container_id` | `containerId` | 容器 id |
| `container_role` | `containerRole` | 建议使用 `metadata_collector` 或平台确认值 |
| `metric_name` | `metricName` | Kafka 分区键 |
| `metric_type` | `metricType` | `gauge`、`counter` 等 |
| `metric_value` | `metricValue` | 指标值 |
| `metric_ts` | `metricTs` | 指标时间戳 |

表侧 metadata 指标值来源如下。这些是指标候选，不表示 `RDW_ODS_FLINK_METRICS` 当前已经存在同名列。

| 指标名 | metrics 事件来源 | 说明 |
|---|---|---|
| `snapshot_count` | Paimon `$snapshots` / Iceberg `snapshots` | 当前可见 snapshot 数 |
| `latest_commit_time` | Paimon `$snapshots.commit_time` / Iceberg `snapshots.committed_at` | 最近一次表级提交时间 |
| `data_file_count` | Paimon `$files` / Iceberg `files content = 0` | 当前可见 data file 数 |
| `avg_data_file_bytes` | Paimon `$files.file_size_in_bytes` / Iceberg `files.file_size_in_bytes` | 平均 data file 大小 |
| `last_file_creation_time` | metadata 或文件系统时间 | 引擎不能提供时允许为空 |
| `manifest_count` | Paimon `$manifests` / Iceberg `manifests` | 当前 manifest 数 |
| `manifest_bytes` | Paimon `$manifests.file_size` / Iceberg `manifests.length` | manifest 总字节数 |
| `metadata_source` | 采集执行器实现路径 | 当前固定为 `spark` |

映射原则：

1. Paimon 与 Iceberg 可以使用不同采样来源，但必须在 metrics Kafka 事件层对齐 `jobName` 和指标命名。
2. 无法采集的字段不得用 `-1` 伪造，应该按 StarRocks schema 允许的空值规则处理；非空字段采集失败时应让本次采样失败。
3. 采样结果只记录必要标签和聚合后的 metadata 指标，不记录完整 catalog 配置、Kafka 连接串或凭据。
4. Spark producer 不生成、不发送 `metric_id`；该字段由 Kafka 到 StarRocks 落库链路生成。

## 9. 调度入口

仓库内现有 `scripts/observe-storage/run.sh` 只能视为临时通用包装器，不是目标设计。

它的严重缺陷如下：

1. 用 `METADATA_COLLECTOR_CMD` 或 `--collector-cmd` 接收整段 shell 命令，导致参数边界不可校验
2. Paimon catalog、Iceberg catalog、metrics Kafka 输出等关键配置被折叠进命令字符串，不利于解释、审计和复现
3. 脚本会把 `collector_cmd` 写入 `sample.meta`，如果命令中夹带地址、用户名或凭据，会扩大敏感信息落盘风险
4. 脚本只知道 `once/loop` 和日志目录，不知道本轮测试的 topic、表、catalog 与阶段规则，不能作为配置来源

因此，目标职责应收敛为：

1. 由外部调度器或明确的采集执行器控制 `once` / `loop`
2. 采集执行器自身负责校验 Paimon/Iceberg catalog 参数、平台作业名和 metrics Kafka 输出
3. 调度层只保存 stdout、stderr、退出码、采样时间和 `collector_run_id`
4. 任何真实连接信息都来自环境变量、外部配置文件或调度系统，不由 shell 包装器拼接生成

它不再负责：

1. 渲染 Flink SQL
2. 调用 `sql-client.sh`
3. 直接写业务 Kafka topic
4. 定义 Paimon 或 Iceberg 的 catalog 配置
5. 定义 Kafka bootstrap、topic 或 consumer group

补充说明：

1. 当前仓库提供调度包装器、StarRocks DDL 和查询模板
2. 当前仓库不应把未经环境确认的依赖版本、连接地址或凭据写死
3. 后续如果实现采集能力，应按当前决策优先实现 Spark 作业，不默认自研 Java collector，也不继续扩大 `run.sh`

## 10. 推荐运行命令

推荐的目标命令形态如下。示例只说明参数边界，不提供真实地址、topic、schema 或凭据。当前执行器形态已选定为 Spark，测试环境 Spark 版本为 `3.2.0`；实现前仍需确认 Hadoop classpath、Paimon/Iceberg connector 依赖和 metadata 访问 SQL/API。

```bash
spark-submit /path/to/table-metadata-metrics-job.jar \
  --emit metrics-kafka \
  --job-name table_metadata_paimon_pk_state \
  --paimon-warehouse "${PAIMON_WAREHOUSE}" \
  --paimon-database "${DATABASE_NAME}" \
  --metrics-topic rdw_ods_flink_metrics \
  --metrics-format json
```

Iceberg 表侧 metadata 采样同理，作业名必须体现 `iceberg` 与被观测表名，并使用 Iceberg 原生 catalog 参数。多表采样由外部编排按脚本或作业拆分，避免在指标事件中重新引入独立 `table_name` 维度。

单次采样由外部调度器直接执行采集执行器。若临时使用 `scripts/observe-storage/run.sh`，只能把它当日志归档包装器，且命令中不得包含凭据：

```bash
bash scripts/observe-storage/run.sh \
  once \
  --output-dir data/out/storage-metrics \
  --label baseline \
  --collector-cmd "/opt/poc/bin/table-metadata-metrics-once.sh"
```

`table-metadata-metrics-once.sh` 属于测试环境外部脚本，不提交到本仓库。它可以在环境内组装 Spark 提交参数，但不得让 `run.sh` 的 `sample.meta` 落盘完整 Kafka 连接串、StarRocks JDBC URL、用户名、密码或 token。

按分钟循环采样建议由外部调度器完成。临时脚本形态如下：

```bash
bash scripts/observe-storage/run.sh \
  loop \
  --output-dir data/out/storage-metrics \
  --label round1 \
  --interval-seconds 60 \
  --iterations 70
```

说明如下：

1. `--output-dir` 只保留执行日志和采样元信息
2. 真正的指标结果写入 metrics Kafka，并通过平台链路落入 StarRocks
3. `--iterations 70` 适合覆盖一轮 70 分钟测试窗口
4. 如果把 `--iterations` 设为 `0`，脚本会持续运行直到被中断
5. 长期方案不应依赖 `METADATA_COLLECTOR_CMD` 传递整段命令；采集执行器应提供类型化参数或平台任务参数校验

## 11. StarRocks 查询入口

StarRocks 查询模板见 `starrocks/storage_metrics_queries.sql`。StarRocks 是最终分析存储，表侧 metadata 指标应先进入 metrics Kafka，再由平台落库链路进入 StarRocks。

推荐固定做三类分析：

1. 按分钟看 `snapshot_count`、`data_file_count`、`manifest_bytes` 趋势
2. 对比 `baseline`、`peak`、`replay`、`recover` 各阶段差异
3. 对比 `paimon` 与 `iceberg` 在同一业务表上的文件膨胀和 metadata 增长速度

## 12. 运行前检查

执行前至少确认以下项目：

1. 表侧 metadata 采集执行器已具备访问 Paimon 与 Iceberg metadata 的能力。
2. 平台 metrics Kafka topic、事件格式、认证、分区键和投递语义已经确认。
3. StarRocks 中已执行或准备好从 `RDW_ODS_FLINK_METRICS` 结构派生的专用分析表 DDL，并已确认 `metric_id` 由 Kafka 到 StarRocks 落库链路生成。
4. Spark 版本为 `3.2.0`，且 Hadoop classpath、Paimon/Iceberg connector 依赖和提交方式已确认。
5. Paimon catalog 参数、Iceberg catalog 参数和 metrics Kafka 输出参数已按本文档分别配置。
6. 业务 Kafka bootstrap、topic 和 consumer group 只在主链路与 lag 观测中配置，不进入表侧 metadata 指标事件。
7. 所有敏感配置都从环境变量、外部配置文件或调度系统注入。
8. 采样元信息不会落盘完整连接串、用户名、密码或 token。

## 13. 推荐实践

如果测试方案要求“每分钟采样 1 次”，推荐做法固定如下：

1. 主写入作业继续跑在 Flink `streaming`
2. 存储层观测独立于主写入作业
3. 由外部调度器每分钟触发表侧 metadata 指标采集执行器
4. Flink 运行态指标和表侧 metadata 指标统一进入 metrics Kafka
5. Kafka 下游统一落入 StarRocks，结论分析在 StarRocks 完成

以下是 Iceberg 元表 `manifests`、`snapshots`、`files` 的完整列字段信息：

## manifests 表字段

|字段名|类型|描述|
|---|---|---|
|path|string|清单文件路径|
|length|long|清单文件大小（字节）|
|partition_spec_id|int|分区规范ID|
|added_snapshot_id|long|添加清单的快照ID|

- `content` 字段值含义：0=数据文件，1=位置删除文件，2=等值删除文件
